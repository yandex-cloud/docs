# Восстановить YDB из резервной копии

Скрипт `ydb-restore.sh` восстанавливает базу данных [{{ iam-name }}](../../concepts/components/iam.md) в YDB из архива, созданного с помощью [скрипта резервного копирования](ydb-backup.md).

Скрипт поддерживается в {{ stackland-name }} версии **26.3 и выше**.

{% note alert %}

Восстановление необратимо удаляет существующую YDB и все ее PVC. Изменения данных {{ iam-name }}, сделанные после создания выбранной резервной копии, будут потеряны.

На время восстановления кластер будет недоступен. Запланируйте окно обслуживания. Если скрипт завершится с ошибкой, кластер может оставаться недоступным до успешного повторного запуска.

{% endnote %}

## Подготовка к работе {#prerequisites}

1. Убедитесь, что на рабочей машине с Linux или macOS установлены `bash`, `awk`, `du`, `kubectl`, `jq`, `tar` и `mktemp`. Запускайте скрипт из интерактивного терминала: перед изменением кластера потребуется подтверждение.
1. Подготовьте kubeconfig с административным доступом к восстанавливаемому кластеру. Доступ должен сохраняться при недоступности {{ iam-name }}. Например, можно использовать kubeconfig с ролью `cluster-admin`, созданный [при установке кластера](../../quickstart.md#installation-common).
1. Подготовьте архив `tar.gz`, созданный скриптом `ydb-backup.sh`. Если текущая YDB доступна и ее данные нужно сохранить, [создайте отдельную резервную копию](ydb-backup.md) перед восстановлением.
1. Убедитесь, что на рабочей машине есть место для распаковки архива. В кластере распакованная копия данных хранится во временном PVC. Его размер скрипт рассчитывает автоматически: объем распакованных данных с запасом 10%, округленный вверх до целого GiB, но не менее 10 GiB. После завершения работы скрипт удаляет временные под и PVC.
1. Укажите абсолютные пути к kubeconfig и архиву. Проверьте выбранный кластер, доступные классы хранилища и читаемость архива:

   ```bash
   KUBECONFIG_PATH="<абсолютный_путь_к_kubeconfig>"
   BACKUP_PATH="<абсолютный_путь_к_архиву.tar.gz>"

   kubectl --kubeconfig "${KUBECONFIG_PATH}" config current-context
   kubectl --kubeconfig "${KUBECONFIG_PATH}" cluster-info
   kubectl --kubeconfig "${KUBECONFIG_PATH}" get storageclass
   tar -tzf "${BACKUP_PATH}" >/dev/null
   ```

1. Выберите `StorageClass` с поддержкой блочных (`volumeMode: Block`) и файловых (`volumeMode: Filesystem`) томов. Скрипт использует этот класс хранилища для новых дисков YDB и временного PVC с резервной копией.

   Для YDB скрипт создаст **девять PVC** размером `100Gi` каждый: по три тома для каждого из трех узлов хранения YDB. Убедитесь, что в выбранном хранилище достаточно свободного места для этих PVC и временного PVC с резервной копией, а в кластере есть не менее трех узлов, на которых могут запускаться поды подготовки дисков.

   После восстановления используется одна группа хранения с выбранным `StorageClass` и тремя дисками на узел, даже если до восстановления конфигурация была другой.

## Восстановить данные {#restore}

1. Сохраните приведенный ниже скрипт в файл `ydb-restore.sh` на рабочей машине.

   {% cut "Скрипт ydb-restore.sh" %}

   {% include notitle [ydb-restore.sh](../../_includes/scripts/operations/iam/ydb-restore.md) %}

   {% endcut %}

1. Сделайте файл исполняемым:

   ```bash
   chmod +x ydb-restore.sh
   ```

1. Укажите выбранный класс хранилища и запустите скрипт:

   ```bash
   STORAGE_CLASS="<имя_StorageClass>"

   ./ydb-restore.sh \
     --kubeconfig "${KUBECONFIG_PATH}" \
     --storage-class "${STORAGE_CLASS}" \
     --timeout 3600 \
     "${BACKUP_PATH}"
   ```

   Где:

   * `--kubeconfig` — обязательный путь к файлу kubeconfig восстанавливаемого кластера.
   * `--storage-class` — обязательное имя существующего `StorageClass` для новых томов YDB и временного PVC с резервной копией.
   * `--timeout` — таймаут ожидания отдельных операций и восстановления дампа YDB в секундах. По умолчанию — `3600`. Это не ограничение на общую длительность работы скрипта.
   * `BACKUP_PATH` — обязательный путь к архиву резервной копии.

1. Проверьте адрес Kubernetes API server и путь к архиву, которые выведет скрипт. Для подтверждения удаления текущих данных введите `yes` в терминале.

1. Дождитесь сообщения `Restore completed successfully`. Не запускайте несколько экземпляров скрипта одновременно и не создавайте резервные копии во время восстановления.

## Проверить результат {#check-result}

1. Проверьте состояние YDB и {{ iam-name }}:

   ```bash
   kubectl --kubeconfig "${KUBECONFIG_PATH}" \
     --namespace stackland-iam \
     get storages.ydb.tech,databases.ydb.tech

   kubectl --kubeconfig "${KUBECONFIG_PATH}" \
     --namespace stackland-iam \
     get deployment iam-operator iam-uber

   kubectl --kubeconfig "${KUBECONFIG_PATH}" \
     --namespace stackland-iam \
     get pvc -l ydb.tech/statefulset-name=ydb-storage
   ```

   Ожидаемый результат:

   * `Storage/ydb-storage` и `Database/ydb-database` находятся в состоянии `Ready`.
   * У `iam-operator` и `iam-uber` есть по одной готовой реплике.
   * Девять PVC находятся в состоянии `Bound` и имеют выбранный `StorageClass`.

1. Войдите в консоль управления и убедитесь, что пользователи и настройки {{ iam-name }} восстановлены из выбранной копии.

## Если восстановление завершилось с ошибкой {#retry}

Устраните причину, указанную в выводе скрипта, и повторите ту же команду с тем же архивом и параметрами. При превышении времени ожидания проверьте состояние ресурсов и при необходимости увеличьте `--timeout`.

Если после ошибки в пространстве имен `stackland-iam` осталась политика `CiliumNetworkPolicy/ydb-restore-block-iam-uber`, не удаляйте ее вручную. Она блокирует обращения {{ iam-name }} к восстанавливаемой базе данных. При повторном запуске скрипт переиспользует политику и удалит ее после восстановления данных.

Повторный запуск также требует подтверждения `yes` и заново пересоздает YDB. Дождитесь сообщения `Restore completed successfully` и выполните [проверку результата](#check-result).
