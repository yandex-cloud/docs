# Создать кластер {{ AF }}

Кластер [{{ AF }}](../../concepts/components/airflow.md) создается ресурсом `AirflowCluster` в пространстве имен [проекта](../projects/create-project.md). Перед созданием кластера администратор установки должен [включить {{ maf-name }}](enable.md).

База метаданных создается автоматически. Настраивать подключение к базе не требуется.

## Перед началом {#before-you-begin}

Подготовьте:

* [включенный компонент {{ maf-name }}](enable.md) и доступный каталог версий — это проверяет администратор установки;
* [пространство имен проекта](../projects/manage-namespaces.md#create-namespace);
* Git-репозиторий с DAG-файлами или S3-совместимое хранилище;
* S3-совместимое хранилище, если нужны удаленные логи задач;
* Secret с учетными данными, если используется внешнее S3-хранилище. Для приватного Git-репозитория консоль управления создает Secret из введенных данных; при создании через CLI подготовьте Secret самостоятельно.

Создайте Secret и ConfigMap, на которые ссылается конфигурация, в том же пространстве имен, что и `AirflowCluster`.

Для автоматически создаваемых бакетов должен быть включен компонент [{{ objstorage-name }}](../../concepts/components/storage.md).

### Права доступа {#permissions}

Доступ к консоли {{ stackland-name }} и доступ к веб-интерфейсу {{ AF }} настраиваются отдельно. [Участие в проекте](../projects/project-roles.md#assign-member) дает возможность видеть проект; для работы с его ресурсами администратор проекта должен [назначить роль с нужными разрешениями](../projects/project-roles.md#create-custom-role).

При подготовке роли учитывайте следующие операции:

#|
|| **Сценарий** | **Разрешения Kubernetes** ||
|| Просмотр списка и карточки кластера | `get`, `list` для `airflowclusters` в группе `airflow.stackland.yandex.cloud` в выбранном пространстве имен. ||
|| Создание, изменение и удаление кластера | Соответственно `create`, `update` и `delete` для `airflowclusters`; для изменения через YAML могут потребоваться права `patch`. ||
|| Выбор версии {{ AF }} | `get` для кластерного ресурса `airflowimagecatalogs` с именем `airflow` в группе `airflow.stackland.yandex.cloud`. Это разрешение выдает администратор установки. ||
|| Выбор существующих Secret и ConfigMap | Чтение соответствующих ресурсов в пространстве имен. Для списков в форме нужно `list`. ||
|| Создание Secret и ConfigMap из введенных данных | Создание и чтение ресурсов, `patch` для привязки к кластеру и `delete` для очистки при ошибке или замене. При ошибке привязки после создания кластера консоль также удаляет созданный `AirflowCluster`. ||
|| Просмотр пароля администратора {{ AF }} | `get` для административного Secret кластера. ||
|#

Для выбора бакетов и AccessKey также нужен доступ к соответствующим ресурсам хранилища. Разрешения на запись DAG-файлов в Git или S3 выдаются отдельно от прав на управление кластером. Если форма сообщает об отказе в доступе, передайте администратору имя проекта, пространство имен, выполняемую операцию и текст ошибки.

Веб-интерфейс {{ AF }} использует собственную учетную запись. Получите ее данные по [инструкции](get-admin-credentials.md); назначение роли в проекте само по себе не создает пользователя {{ AF }}.

## Через консоль управления {#console}

1. В консоли управления {{ stackland-name }} выберите проект и пространство имен.
1. В левом меню выберите **Кластеры Airflow**. Если пункт скрыт, раскройте **Ещё**. Нажмите **Создать кластер**.
1. В разделе **Основные настройки** укажите:

    * **Имя кластера** — уникальное имя в выбранном пространстве имен.
    * **Версия Airflow** — версию из доступного списка.
    * **Защита от удаления** — включите, чтобы предотвратить случайное удаление кластера. По умолчанию выключена.
    * **Публичный доступ** — оставьте включенным, чтобы открывать веб-интерфейс по HTTPS. При выключенном доступе потребуется [перенаправление порта](connect-ui.md#private-access).

1. В разделе **DAG** выберите **Источник** и настройте [Git-репозиторий](#console-git) или [S3-хранилище](#console-s3).
1. При необходимости в разделе **Компоненты** задайте количество реплик и ресурсы планировщика, API-сервера, обработчика триггеров и обработчика DAG.

    Оставьте поля пустыми, чтобы использовать значения по умолчанию. Если задаете ресурсы компонента, заполните CPU и память в обеих группах: **Запросы** и **Лимиты**. Например, запрос CPU — `500m`, памяти — `1Gi`, лимит CPU — `1`, памяти — `2Gi`. Запрос не должен превышать лимит. Количество реплик должно быть не меньше `1`.

1. Чтобы сохранять логи после пересоздания подов, в разделе **Логи задач** включите **Хранить логи удалённо** и настройте хранилище [так же, как для DAG в S3](#console-s3). Для DAG и логов используйте разные бакеты или разные пути внутри бакета.
1. Если DAG требуют дополнительных библиотек, заполните раздел **Дополнительные зависимости** по [инструкции](edit-cluster.md#console-dependencies). При необходимости добавьте [параметры airflow.cfg](edit-cluster.md#console-config).
1. Нажмите **Создать**. Откройте созданный кластер и дождитесь состояния `Ready`.

    Если создание не завершается, откройте вкладку **Состояния** и проверьте причины неготовности. Рекомендации приведены в разделе [Устранение неполадок](troubleshooting.md).

### Git-репозиторий {#console-git}

В поле **Источник** выберите **Git-репозиторий** и заполните раздел **Git-источник DAG**:

* **Адрес репозитория** — HTTPS- или SSH-адрес, например `https://git.example.com/team/airflow-dags.git` или `git@git.example.com:team/airflow-dags.git`.
* **Git ref** — ветку, тег или коммит, например `main`.
* **Путь к DAG** — каталог внутри репозитория, например `dags`. Для корня репозитория оставьте поле пустым.

Для приватного HTTPS-репозитория в разделе **Доступ к репозиторию** включите **Использовать аутентификацию** и укажите **Имя пользователя** и **Пароль**. Вместо пароля можно использовать токен доступа, если это поддерживает ваш Git-сервис.

Для SSH включите **Использовать аутентификацию**, загрузите **Приватный SSH-ключ** и **Файл known_hosts** с ключом сервера. Получите проверенный файл `known_hosts` у администратора Git-сервиса.

Консоль создаст необходимые Secret и ConfigMap. Не включайте учетные данные в адрес репозитория.

### S3-хранилище {#console-s3}

В поле **Источник** выберите **S3-хранилище**. В разделе **S3-источник DAG** задайте **Тип хранилища**:

{% list tabs %}

- Stackland Storage

    Для {{ objstorage-name }} в {{ stackland-name }} выберите **Stackland Storage**:

    * **Способ настройки бакета** — **Создать автоматически** или **Выбрать существующий**. Во втором случае укажите **Существующий бакет** из выбранного пространства имен.
    * **Способ настройки AccessKey** — **Создать автоматически** или **Выбрать существующий**. Во втором случае укажите **Существующий AccessKey**. Его права должны разрешать доступ к бакету.
    * **Путь в bucket** — префикс объектов с DAG-файлами, например `dags/`. Не добавляйте `/` в начале пути. Пустое поле означает корень бакета.

    При автоматической настройке оператор создаст бакет и ресурсы доступа. Имена созданных ресурсов появятся в карточке кластера.

- Внешний S3

    Для внешнего S3-совместимого хранилища выберите **Внешний S3**:

    * **Имя бакета** — имя существующего бакета.
    * **Secret с credentials** — Secret с ключами доступа в том же пространстве имен. До заполнения формы [создайте его через CLI](#external-s3) или попросите администратора подготовить этот ресурс: в форме выбирается уже существующий Secret.
    * **Ключ с Access Key ID** и **Ключ с Secret Access Key** — имена записей в Secret, например `access-key-id` и `secret-access-key`.
    * **Endpoint URL**, **Регион** и **Использовать path-style addressing** — настройки подключения вашего S3-сервиса.
    * **Путь в bucket** — префикс DAG-файлов, например `dags/`, или пустое поле для корня бакета.

    Если эндпоинт использует собственный центр сертификации, в поле **Custom CA** выберите **Загрузить сертификат** и загрузите CA-сертификат в формате PEM либо выберите **Существующий ресурс** и укажите Secret или ConfigMap и ключ сертификата.

{% endlist %}

Для удаленного хранения логов эти же поля доступны в разделе **Логи задач** после включения **Хранить логи удалённо**. Ключ доступа должен разрешать запись логов и их чтение.

## Через CLI {#create}

Проверьте доступные версии {{ AF }}:

```bash
kubectl get airflowimagecatalog airflow \
  -o jsonpath='{range .spec.images[*]}{.version}{"\n"}{end}'
```

Если команда не выводит версии, посмотрите структуру ресурса: `kubectl get airflowimagecatalog airflow -o yaml`.

1. Создайте файл ресурса `AirflowCluster`, например `airflow-cluster.yaml`, и вставьте одну из конфигураций:

    {% list tabs %}

    - Git и локальные логи

        Пример использует публичный Git-репозиторий и локальные логи задач.

        {% include notitle [YAML-файл](../../_includes/yamls/operations/airflow/create-cluster-external.md) %}

    - {{ objstorage-name }} для DAG и логов

        Пример создает отдельные бакеты для DAG-файлов и логов задач. DAG-файлы загружаются из префикса `dags/` в бакете.

        {% include notitle [YAML-файл](../../_includes/yamls/operations/airflow/create-cluster-managed.md) %}

    {% endlist %}

1. Укажите имя кластера в `metadata.name` и доступную версию в `spec.version`. Для Git-источника замените URL репозитория и значение `ref` на свои.

    В обоих примерах включены публичный доступ к веб-интерфейсу (`spec.publicAccess: true`) и [защита от удаления](../../concepts/components/airflow.md#deletion-protection) (`spec.deletionProtection: true`). При необходимости измените эти параметры.

1. Примените манифест:

    ```bash
    kubectl apply -f airflow-cluster.yaml -n <пространство_имен>
    ```

    Пространство имен также можно указать в `metadata.namespace` манифеста и не передавать параметр `-n` в команде.

1. Дождитесь состояния `Ready`, подставив имя кластера из `metadata.name`:

    ```bash
    kubectl get airflowcluster <имя_кластера> \
      -n <пространство_имен> \
      -w
    ```

1. Если кластер долго остается в `Provisioning` или переходит в `Failed`, проверьте условия состояния в `status.conditions`:

    ```bash
    kubectl describe airflowcluster <имя_кластера> -n <пространство_имен>
    ```

    Рекомендации приведены в разделе [Устранение неполадок](troubleshooting.md).

## Приватный Git-репозиторий {#private-git}

Для HTTPS создайте Secret с фиксированными ключами `username` и `password`:

```bash
kubectl create secret generic airflow-git-auth \
  -n <пространство_имен> \
  --from-literal=username=<имя_пользователя> \
  --from-literal=password=<токен_или_пароль>
```

Добавьте ссылку в `spec.dags.git.authSecretRef` манифеста:

```yaml
spec:
  dags:
    source: git
    git:
      repo: https://git.example.com/team/airflow-dags.git
      ref: main
      authSecretRef:
        name: airflow-git-auth
```

Для SSH Secret должен содержать ключ `ssh-privatekey`, а ConfigMap — ключ `known_hosts`:

```yaml
spec:
  dags:
    source: git
    git:
      repo: git@git.example.com:team/airflow-dags.git
      ref: main
      authSecretRef:
        name: airflow-git-ssh
      knownHostsConfigMapRef:
        name: airflow-git-known-hosts
```

Интервал синхронизации Git и S3 составляет 60 секунд и не настраивается.

## Внешнее S3-хранилище {#external-s3}

Создайте Secret с ключами доступа:

```bash
kubectl create secret generic airflow-s3-credentials \
  -n <пространство_имен> \
  --from-literal=access-key-id=<идентификатор_ключа> \
  --from-literal=secret-access-key=<секретный_ключ>
```

Для DAG-файлов задайте в `spec`:

```yaml
spec:
  dags:
    source: s3
    s3:
      type: s3
      s3:
        bucket: airflow-dags
        region: ru-central1
        endpointUrl: https://storage.yandexcloud.net
        credentialsSecretRef:
          name: airflow-s3-credentials
          accessKeyIdPath: access-key-id
          secretAccessKeyPath: secret-access-key
        subPath: dags/
```

Для удаленных логов задайте в `spec` поле `taskLogs`:

```yaml
spec:
  taskLogs:
    type: s3
    s3:
      bucket: airflow-logs
      region: ru-central1
      endpointUrl: https://storage.yandexcloud.net
      credentialsSecretRef:
        name: airflow-s3-credentials
        accessKeyIdPath: access-key-id
        secretAccessKeyPath: secret-access-key
      subPath: logs/
```
