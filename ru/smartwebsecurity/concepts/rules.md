# Правила

_Правило_ определяет [условия](conditions.md) отбора HTTP-запросов и [действие](#rule-action), которое применяется к ним. Если запрос соответствует нескольким правилам, итоговое действие определяется их [приоритетами](#rules-order).

Инструкции по настройке приведены в разделе [Управление правилами](../operations/index.md#rules).

## Типы правил {#rule-types}

В сервисе предусмотрены следующие типы правил:

* [Базовые](#base-rules)
* [Smart Protection](#smart-protection-rules)
* [Web Application Firewall](#waf-rules)
* [Advanced Rate Limiter](#arl-rules)

Также существует внутреннее [сервисное правило](#service-rule), которое может срабатывать при атаках.

### Базовые правила {#base-rules}

_Базовое правило_ позволяет управлять доступом по параметрам HTTP-запросов, например IP-адресу клиента, пути запроса или заголовкам. Запросы можно разрешить, запретить или направить на [капчу](#captcha-settings). Например, можно разрешить запросы с доверенных IP-адресов или включить проверку с помощью капчи для страницы входа.

В каждом [профиле безопасности](profiles.md) есть _базовое правило по умолчанию_ с самым низким приоритетом. Оно разрешает или запрещает запросы, которые не попали под условия других правил профиля.

### Правила Smart Protection {#smart-protection-rules}

_Smart Protection_ анализирует трафик по заданным условиям с помощью алгоритмов машинного обучения и поведенческого анализа. Правило обеспечивает защиту от DDoS на уровне L7 и поддерживает [полную защиту и защиту API](#smart-protection-actions).

### Правила WAF + Smart Protection {#waf-rules}

Правило _Web Application Firewall_ (WAF) подключает [профиль WAF](waf.md) с [наборами базовых правил](waf.md#rules-set) для анализа трафика. Оно также включает Smart Protection и поддерживает те же [действия](#smart-protection-actions). При подключении WAF отдельное правило Smart Protection для того же трафика не требуется.

### Правила Advanced Rate Limiter {#arl-rules}

Правило _Advanced Rate Limiter_ (ARL) ограничивает количество запросов за определенный промежуток времени. Лимит можно задать для всего трафика или его сегментов.

Правила настраиваются в отдельном [профиле ARL](arl.md), который подключается к профилю безопасности. Доступные [действия](#arl-rule-actions) применяются к запросам сверх лимита.

## Действия правил {#rule-action}

Доступные действия зависят от типа правила. Запросы, разрешенные всеми правилами и пропущенные к защищаемому ресурсу, называются _легитимными_.

Для единообразного оформления ответов клиентам при срабатывании правил можно создать собственные [шаблоны ответов](response-templates.md).

### Базовые правила {#base-rule-actions}

Для базовых правил можно выбрать действия:

* _{{ ui-key.yacloud.smart-web-security.overview.cell_sec-action-deny }}_ — заблокировать запросы.
* _{{ ui-key.yacloud.smart-web-security.overview.cell_sec-action-allow }}_ — пропустить запросы.
* _{{ ui-key.yacloud.smart-web-security.overview.cell_sec-action-captcha }}_ — направить клиента на [капчу](#captcha-settings).

### Smart Protection и WAF {#smart-protection-actions}

Для правил Smart Protection и WAF доступны два режима:

* _{{ ui-key.yacloud.smart-web-security.overview.cell_mode-full }}_ — подозрительные запросы отправляются на одну из [проверок](#client-checks): JS Challenge, Cookie Challenge или капчу. Smart Protection автоматически выбирает проверку на основе анализа запроса.
* _{{ ui-key.yacloud.smart-web-security.overview.cell_mode-api }}_ — запросы не отправляются на дополнительные проверки, но политики защиты блокируют явные попытки атак. Запрос, который в режиме полной защиты был бы направлен на проверку, в этом режиме может быть пропущен к ресурсу.

Используйте режим _Защита API_ для эндпоинтов:

* мобильных приложений;
* с автоматизированными вызовами;
* с динамической загрузкой контента (`ajax`, `xhr`, `iframe`).

### Advanced Rate Limiter {#arl-rule-actions}

Для запросов сверх лимита можно выбрать действия:

* _{{ ui-key.yacloud.smart-web-security.arl.label_rule-action-deny_3kenc }}_ — блокировать запросы до окончания периода, на который установлен лимит.
* _Временно блокировать все запросы_ — после превышения лимита блокировать запросы на фиксированный период от одной секунды до 24 часов.
* _{{ ui-key.yacloud.smart-web-security.arl.label_rule-action-captcha }} запросы свыше лимита_ — направить клиента в {{ captcha-name }}.

При блокировке клиент получает ошибку `429`. [Капча](#captcha-settings) позволяет проверить запросы сверх лимита без немедленной блокировки.

{% note warning %}

Не используйте капчу для HTTP-запросов с динамической загрузкой контента (`ajax`, `xhr`, `iframe`) и запросов к мобильным приложениям.

{% endnote %}

## Проверки JS Challenge, Cookie Challenge и капча {#client-checks}

В режиме [полной защиты](#smart-protection-actions) Smart Protection пропускает запрос к ресурсу или автоматически выбирает проверку для подозрительного трафика:

* _JS Challenge_ — автоматически проверяет выполнение JavaScript-кода на стороне клиента.
* _Cookie Challenge_ — автоматически проверяет, может ли клиент сохранить cookie и передать его в следующем запросе.
* _Капча_ — направляет пользователя в [{{ captcha-name }}](../../smartcaptcha/), где может потребоваться выполнить [задание](../../smartcaptcha/concepts/tasks.md).

В [нормальном](profiles.md#protection-mode) режиме на капчу направляются только однозначно роботизированные запросы, которые Smart Protection определяет по высокому значению [Bot score](conditions.md). Остальные запросы направляются на JS Challenge или Cookie Challenge, либо пропускаются без дополнительной проверки.

Успешное выполнение JS Challenge или Cookie Challenge не доказывает, что запрос отправил человек: автоматизированные браузеры тоже поддерживают JavaScript и cookie. При этом запрет JavaScript или cookie может помешать проверке легитимного клиента.

## Режимы применения правил {#protection-modes}

Для каждого правила профиля безопасности выбирается набор [режимов защиты](profiles.md#protection-mode), в которых оно действует:

* **Все режимы** (по умолчанию).
* **«Повышенная защита» и «Под атакой»**.
* **«Под атакой»**.

При переключении режима профиля начинает действовать выбранный набор правил.

Режимы применения задаются при [добавлении](../operations/rule-add.md) или [изменении](../operations/rule-update.md) правила и отображаются в таблице правил профиля.

## Общие принципы работы правил {#rules-order}

Сначала запросы обрабатываются правилами профиля безопасности. Затем разрешенные запросы проверяются правилами профиля ARL, если он подключен. Приоритеты в этих профилях независимы друг от друга.

### Профиль безопасности {#security-profile-rules-order}

Приоритет правила задается числом от `1` до `1000000`. Правила, активные в текущем [режиме защиты](profiles.md#protection-mode), срабатывают одновременно. Одному запросу могут соответствовать несколько правил. Итоговое действие определяется правилом с наивысшим приоритетом.

{% include [preconfigured-rules-priority](../../_includes/smartwebsecurity/preconfigured-rules-priority.md) %}

Назначайте более высокий приоритет:

* правилам, которые разрешают запросы;
* правилам с условиями фильтрации по конкретным параметрам.

Иначе к запросу могут примениться общие правила с более широкими условиями.

{% include [waf-priority-rules](../../_includes/smartwebsecurity/waf-priority-rules.md) %}

### Профиль ARL {#arl-profile-rules-order}

Правила ARL могут блокировать запросы, разрешенные профилем безопасности. Если такой трафик не нужно ограничивать, исключите его из [условий правил ARL](arl.md#traffic-conditions).

Чем меньше число, тем выше приоритет правила ARL. Значения приоритета можно выбирать произвольно. Пример порядка правил:

Приоритет | Имя правила | Действие | Описание правила
--- | --- | --- | ---
1000 | arl-rule-1 | Блокировать запросы свыше лимита | Ограничение общей нагрузки на ресурс
2000 | arl-rule-2 | Временно блокировать все запросы | Защита от ботов, парсеров, брутфорса, спама
3000 | arl-rule-3 | Отправлять на капчу запросы свыше лимита | Проверка браузерных клиентов при превышении лимита

### Режим «Только логирование» {#dry-run}

Режим `Только логирование` позволяет проверить условия и приоритеты правил перед включением защиты. Правило записывает в логи информацию о подходящих запросах, но не применяет к ним действие. Для правил ARL фиксируются превышения лимита.

Такие правила не влияют на обработку трафика: применяется следующее подходящее правило по приоритету, для которого включена защита. В частности, правило Smart Protection в режиме `Только логирование` не обеспечивает защиту от DDoS.

Для правил профиля безопасности поле `dry_run_matched_rule_verdict` содержит ожидаемое действие правила в режиме `Только логирование`. Фактическое действие над запросом отражается в поле `action`. Подробнее о [полях логов](logging.md#log-contents) и [фильтрах для правил в режиме логирования](../operations/configure-logging.md#dry-run-filters).

## Сервисное правило {#service-rule}

Для усиления защиты от атак {{ sws-name }} может блокировать вредоносные запросы, даже если профиль безопасности их разрешает. Остальные запросы обрабатываются по настройкам профиля.

При срабатывании сервисного правила в [логах](logging.md) появляется отметка `sws_service_rule`. Примеры логов:

* В сервисе {{ sws-name }}:

    ```text
    matched_rule_name: "sws_service_rule",
    matched_rule_type: "SMART_PROTECTION",
    matched_rule_verdict: "DENY",
    ```

* В сервисе [{{ alb-full-name }}](../../application-load-balancer/):

    ```json
    "matched_rule": {
      "dry_run": "false",
      "rule_name": "sws_service_rule",
      "rule_type": "SMART_PROTECTION",
      "verdict": "DENY"
    }
    ```
