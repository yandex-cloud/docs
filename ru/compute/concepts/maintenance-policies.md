# Политики обслуживания виртуальных машин


*Политики обслуживания* (Compute Maintenance Policies) позволяют управлять реакцией ВМ на плановое обслуживание и получать информацию о нем с помощью [метаданных](vm-metadata.md).

В ходе обслуживания виртуальная машина переносится на другой хост. Политика определяет способ переноса:

* С помощью перезапуска на другом хосте.
* С помощью [динамической миграции](live-migration.md) на другой хост без перезапуска.

Если политика настроена, информация о предстоящем обслуживании может записываться в метаданные виртуальной машины. Метаданные об обслуживании хранятся в сервисе метаданных и доступны только изнутри виртуальной машины. Приложения на ВМ могут читать их и подготовиться к обслуживанию — например, перед перезапуском завершить текущие запросы или сохранить состояние.

## Параметры политики обслуживания {#parameters}

{% note warning %}

Перед настройкой политики ознакомьтесь с [особенностями для разных типов ВМ](#vm-specifics). Доступные типы политик и поведение при обслуживании зависят от типа ВМ.

{% endnote %}

Политика обслуживания ВМ задается двумя параметрами:

* `maintenance_policy` — тип политики обслуживания. 
* `maintenance_grace_period` — время ожидания перед началом обслуживания.

Тип политики (`maintenance_policy`) определяет, каким способом виртуальная машина будет перенесена на другой хост. Если с помощью перезапуска, то параметр должен иметь значение `RESTART`. Если динамической миграцией, то `MIGRATE`.

Можно явно указать, что политика не задана, с помощью значения `MAINTENANCE_POLICY_UNSPECIFIED`. В этом случае информация об обслуживании в метаданных не появляется, ожидания перед обслуживанием нет.

Время ожидания (`maintenance_grace_period`) определяет, на сколько будут отложены перезапуск или миграция виртуальной машины.

Максимальное время ожидания:

* До одной минуты для ВМ без GPU.
* До одного часа для ВМ с GPU.

Информация об обслуживании появляется в метаданных ВМ только при `maintenance_grace_period > 0`. При нулевом значении информация не появляется и обслуживание выполняется без ожидания.

Политику обслуживания можно настроить при [создании](../operations/index.md#vm-create) и [изменении](../operations/vm-control/vm-update.md) ВМ. С помощью [CLI](../../cli/index.yaml), [{{ TF }}](../../tutorials/infrastructure-management/terraform-quickstart.md) или [API](../api-ref/index.md) настраиваются тип политики и время ожидания, а в консоли управления можно настроить только тип политики.

## Работа с метаданными {#handle-event}

Информация о предстоящем обслуживании записывается в метаданные виртуальной машины по ключу `/instance/maintenance-event`. Доступ по ключу можно получить [только изнутри ВМ](../concepts/metadata/accessing-metadata.md) с помощью [сервиса метаданных](vm-metadata.md). Подробнее [о формате хранения метаданных](vm-metadata.md#metadata-formats).

Записываются следующие значения:

* `TERMINATE_ON_HOST_MAINTENANCE` перед перезапуском виртуальной машины.
* `MIGRATE_ON_HOST_MAINTENANCE` перед динамической миграцией.

Вы можете реализовать [чтение метаданных изнутри ВМ](../operations/vm-metadata/get-vm-metadata.md#internal-access) и реакцию на обслуживание в своем приложении.

Например, настроена политика `RESTART`. В метаданные запишется значение `TERMINATE_ON_HOST_MAINTENANCE`. Начнется отсчет `maintenance_grace_period`. Приложение прочитает метаданные и за время ожидания сохранит свое состояние. По истечении времени ожидания ВМ перезапустится.

Чтобы проверить реакцию на обслуживание в своем приложении, [симулируйте событие обслуживания](../operations/vm-control/vm-update-policies.md#simulate).

## Особенности для разных типов ВМ {#vm-specifics}

### Особенности для прерываемых ВМ {#preemptible-vm}

[Прерываемые ВМ](preemptible-vm.md) при обслуживании останавливаются и не мигрируют. Информация об обслуживании в метаданных не появляется.

### Особенности для ВМ с GPU {#vm-with-gpu}

Для ВМ с GPU [динамическая миграция не поддерживается](live-migration.md#limitations).

Если для непрерываемой ВМ с GPU настроена политика `RESTART`, [уведомления по электронной почте](../../resource-manager/concepts/notify.md#technical) о планируемых работах отключаются, а [задания на техническое обслуживание](./gpus-maintenance.md#tasks) не создаются. При планируемых работах ВМ автоматически перезапускается после ожидания `maintenance_grace_period`.

## Ограничения {#limits}

События в метаданных предупреждают только о плановом обслуживании. При неисправности ВМ может быть перезапущена на другом хосте без предупреждения. Уведомление о [сбое](../../resource-manager/concepts/notify.md#infra) придет по электронной почте.
