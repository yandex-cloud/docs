# Хранилище в {{ mrd-name }}



{{ mrd-name }} позволяет использовать сетевые и локальные диски для организации хранилища кластеров баз данных. Сетевые диски реализованы на базе сетевых блоков — виртуальных дисков в инфраструктуре {{ yandex-cloud }}. Локальные диски физически размещаются в серверах хостов БД.

{% include [storage-type](../../_includes/mdb/mvk/storage-type.md) %}

## Выбор типа диска при создании кластера {#storage-type-selection}

Количество хостов, которые можно создать вместе с кластером {{ VLK }}, зависит от выбранного типа диска и того, включено ли [шардирование](./sharding.md):

| Тип дисков                                                             | Нешардированный кластер  | Шардированный кластер    |
| ------------------------------------------------------------------------- | --------------------------------- | ----------------------------------|
| Сетевые SSD-диски (`network-ssd`), сверхбыстрые сетевые SSD-диски с тремя репликами (`network-ssd-io-m3`)                           | ⩾ 1 хоста                         | ⩾ 1 хоста (1 шард × 1 хост)     |
| Локальные SSD-диски (`local-ssd`)                           | ⩾ 3 хостов                        | ⩾ 2 хостов (1 шард × 2 хоста)    |
| Нереплицируемые SSD-диски (`network-ssd-nonreplicated`)     | ⩾ 3 хостов                        | ⩾ 3 хостов (1 шард × 3 хоста)    |

Информация об ограничениях на количество хостов в кластере или шарде приведена в разделе [Квоты и лимиты](./limits.md).


## Управление дисковым пространством {#manage-storage-space}

Когда хранилище заполняется на 100%, хосты кластера автоматически переходят в режим read-only. В этом режиме запросы на запись данных завершаются ошибкой. Чтобы вывести кластер из режима read-only, [увеличьте размер хранилища](../operations/update.md#change-disk-size) или обратитесь в [техническую поддержку]({{ link-console-support }}).

### Отслеживание перехода в read-only {#read-only-monitor}

Чтобы отслеживать степень заполнения хранилища кластера, настройте алерты в {{ monitoring-full-name }}:

1. В [консоли управления]({{ link-console-main }}) выберите каталог.
1. [Перейдите]({{ link-monitoring }}) в сервис **{{ ui-key.yacloud.iam.folder.dashboard.label_monitoring }}**.
1. [Создайте канал уведомлений](../../monitoring/operations/alert/create-channel.md).
1. [Создайте алерт](../../monitoring/operations/alert/create-alert.md) со следующими параметрами:

   * Выражение для метрики — `disk.used_bytes / disk.total_bytes * 100`.

   * **{{ ui-key.yacloud_monitoring.alert.title_conditions }}** — задайте условия срабатывания алерта:

      * **{{ ui-key.yacloud_monitoring.alert.label_evaluation-type }}** — `{{ ui-key.yacloud_monitoring.alert-template.threshold-type.max }}` (максимальное значение метрики за период).
      * **{{ ui-key.yacloud_monitoring.monitoring-alerts.threshold-table.trigger-condition }}** — `{{ ui-key.yacloud_monitoring.alert.title_comparison-gte }}`.
      * **{{ ui-key.yacloud_monitoring.alert.status_warn }}** — `90` (90 % от размера хранилища).
      * **{{ ui-key.yacloud_monitoring.alert.status_alarm }}** — `95` (95 % от размера хранилища).
      * **{{ ui-key.yacloud_monitoring.alert.label_evaluation-window }}** — период, за который будет вычисляться значение метрики.
      * **{{ ui-key.yacloud_monitoring.monitoring-alerts.title.time-shift }}** — предпочтительный сдвиг по времени назад в секундах. Позволяет исключить некорректные срабатывания алерта с несколькими метриками, которые собираются с разным интервалом. Подробнее о задержке вычисления в [документации {{ monitoring-full-name }}](../../monitoring/concepts/alerting/alert.md#evaluation-delay).

   * **Уведомления** — добавьте созданный ранее канал уведомлений.

### Автоматическое увеличение размера хранилища {#auto-rescale}

Автоматическое увеличение размера хранилища позволяет избежать ситуаций, когда свободное место на диске закончилось и хосты перешли в режим read-only. Хранилище увеличивается, когда достигнут установленный порог срабатывания — процент от общего объема хранилища. Есть два порога:

* Порог для планового увеличения. Когда он достигнут, объем хранилища увеличивается во время ближайшего [окна обслуживания](maintenance.md#maintenance-window). Если задан этот порог, [настройте](../operations/update.md#change-additional-settings) расписание обслуживания.
* Порог для незамедлительного увеличения. Когда он достигнут, объем хранилища увеличивается немедленно.

Можно использовать один либо оба порога. Если заданы оба, порог для незамедлительного увеличения должен быть выше, чем порог для планового.

{% include [storage-resize-steps](../../_includes/mdb/mvk/storage-resize-steps.md) %}

Настроить автоматическое увеличение размера хранилища можно при [создании](../operations/cluster-create.md) или [изменении](../operations/update.md#disk-size-autoscale) кластера.

## Многоуровневое хранилище {#data-tiering}

В {{ VLK }} все данные хранятся в оперативной памяти. Это обеспечивает высокую скорость работы, но требует большого объема оперативной памяти, которая значительно дороже дискового пространства.

Многоуровневое хранение данных (data tiering) позволяет переносить неиспользуемые данные из памяти на диск. Таким образом, данные могут храниться и в оперативной памяти, и в дисковом хранилище.

Для управления данными используется политика удаления ключей, указываемая в настройке [Maxmemory policy](settings-list.html#settings-maxmemory-policy). В {{ VLK }} при включении такой политики вытесненные данные удаляются. При включенном многоуровневом хранении вместо удаления данные переносятся на диск, т. е. охлаждаются.

При запросе {{ VLK }} сначала ищет данные в оперативной памяти. Если данных там нет, {{ VLK }} ищет их в дисковом хранилище.

Если свободное место на диске заканчивается, ключи удаляются так же, как при обычном вытеснении.

{% note warning %}

При включенной политике `noeviction` данные будут попадать на диск по достижении `maxmemory`, но не будут удаляться с диска при его заполнении.

{% endnote %}

Многоуровневое хранение позволяет экономить оперативную память, перенося редко используемые данные на диск. Это может быть полезно, когда общий объем данных значительно превышает объем часто используемых данных.

Например, в БД хранится 300 ГБ данных, но активно используется только 20%, т. е. 60 ГБ. Без многоуровневого хранения весь объем данных должен находиться в оперативной памяти. При включении многоуровневого хранения 240 ГБ редко используемых данных можно перенести на диск и хранить в памяти только часто используемые данные. Это позволяет вместо более чем 300 ГБ оперативной памяти использовать около 60–70 ГБ с минимальным падением времени отклика.

В отличие от гибридных хранилищ, при таком подходе объектное хранилище S3 не используется: данные переносятся непосредственно из памяти на диск.
