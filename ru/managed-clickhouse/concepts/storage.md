# Хранилище в {{ mch-name }}


{{ mch-name }} позволяет использовать сетевые и локальные диски для организации хранилища кластеров баз данных. Сетевые диски реализованы на базе сетевых блоков — виртуальных дисков в инфраструктуре {{ yandex-cloud }}. Локальные диски физически размещаются в серверах хостов БД.

{% include [storage-type](../../_includes/mdb/mch/storage-type.md) %}



## Гибридное хранилище {#hybrid-storage-features}

Гибридное хранилище {{ mch-name }} сочетает в себе два уровня хранения данных:

* кластерное хранилище — часто используемые данные (горячие данные) размещаются на быстрых носителях (сетевых дисках кластера);
* объектное хранилище — редко используемые данные (холодные данные) размещаются в более дешевом и медленном хранилище [{{ objstorage-full-name }}](../../storage/).

Новые данные записываются в кластерное или объектное хранилище в соответствии с настроенными [политиками](#storage-policies). Например, для политики по умолчанию новые данные сначала записываются в кластерное хранилище. Все операции с ними происходят в соответствии с принципами работы {{ CH }}, включая разбиение на разделы (partitions) и куски данных (parts). Далее {{ CH }} отслеживает частоту доступа к данным и автоматически перемещает их в объектное хранилище. Обратное перемещение (из объектного хранилища в кластерное) автоматически не выполняется, но это можно сделать вручную с помощью команд `MOVE PARTITION` и `MOVE PART`.

В объектном хранилище используется служебный бакет с неограниченным объемом памяти. [Класс такого хранилища](../../storage/concepts/storage-class.md) — стандартный, изменить его нельзя. Для объектного хранилища применяются [лимиты сервиса {{ objstorage-name }}](../../storage/concepts/limits.md).


Хранение холодных данных и их резервных копий в гибридном хранилище учитывается при расчете [стоимости использования кластера](../pricing.md#rules-storage).


Включить гибридное хранилище можно при [создании](../operations/hybrid-storage.md#cluster-create) или [изменении](../operations/hybrid-storage.md#cluster-update) кластера.

{% include [Hybrid Storage cannot be switched off](../../_includes/mdb/mch/hybrid-storage-cannot-be-switched-off.md) %}


### Преимущества и недостатки гибридного хранилища {#advantages}

Основные преимущества использования гибридного хранилища:

* Актуальные данные обрабатываются очень быстро, благодаря хранению на быстрых сетевых дисках. Это обеспечивает низкую задержку и высокую скорость выполнения аналитических запросов.
* Редко используемые данные размещаются в более дешевом объектном хранилище, что позволяет снизить затраты на хранение.
* Автоматическое управление данными. Данные могут переноситься между уровнями хранения по определенным условиям: из-за заполненности диска, по истечении заданного срока с помощью параметра [TTL](#ttl) или вручную.
* Более простое масштабирование. При добавлении новой реплики в кластер с гибридным хранилищем в нее копируются только часто используемые данные с сетевых дисков, а данные в объектном хранилище не дублируются. Это экономит ресурсы и ускоряет процесс масштабирования.
* Единый интерфейс для доступа к данным. {{ CH }} скрывает детали хранения от потребителей данных, позволяя выполнять как редкие запросы к холодным данным, так и частые — к горячим, через единый интерфейс.

Недостатки гибридного хранилища:

* Низкая скорость доступа к объектному хранилищу.
* Гибридное хранилище доступно только для таблиц на [движке MergeTree]({{ ch.docs }}{{ lang }}/engines/table-engines/mergetree-family/mergetree). Данные таблиц на других движках хранятся только в кластерном хранилище.
* Если в кластере включено гибридное хранение данных, то вернуться к обычному хранению данных нельзя.


### Доступные политики хранения {#storage-policies}

Распределять данные между кластерным и объектным хранилищами можно с помощью политик хранения, заданных для таблиц базы данных.

{% note info %}

Создавать новые политики хранения или изменять уже существующие нельзя.

{% endnote %}

В кластере {{ mch-name }} с включенным гибридным хранилищем доступны следующие политики хранения:

* `default` (по умолчанию) — кластер автоматически управляет размещением данных в зависимости от:

    * [настроек гибридного хранилища](#hybrid-storage-settings);
    * настроек [TTL](#ttl) для таблиц.

* `local` — строки таблицы с такой политикой размещаются только в кластерном хранилище. Перемещение данных между хранилищами не происходит.

* `object_storage` — строки таблицы с такой политикой размещаются только в объектном хранилище. Перемещение данных между хранилищами не происходит.

Выбор политики хранения не оказывает влияния на операции слияния кусков данных.

Подробнее о политиках хранения и их настройках читайте в [документации {{ CH }}]({{ ch.docs }}{{ lang }}/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-multiple-volumes).


### Операции слияния {#merger-operations}

При вставке данных в таблицы семейства MergeTree создаются новые неизменяемые куски, отсортированные по первичному ключу. Со временем их количество может вырасти, что приводит к накладным расходам при обработке запросов. Чтобы решить эту проблему, {{ CH }} периодически выполняет фоновые слияния мелких кусков данных в более крупные.

На [операции слияния]({{ ch.docs }}{{ lang }}/engines/table-engines/mergetree-family/custom-partitioning-key) влияют следующие [настройки гибридного хранилища](#hybrid-storage-settings):

* [prefer_not_to_merge](#hybrid-storage-settings) — включает/отключает слияние кусков данных в объектном хранилище.
* `max_data_part_size_bytes` — устанавливает максимальный размер итогового куска данных после слияния меньших кусков в объектном хранилище. Настройку можно задать только через обращение в [техническую поддержку]({{ link-console-support }}).

Влиять на поведение операций слияния можно также с помощью доступных в кластере [настроек](./settings-list.md). Найти их можно поиском по слову «merge». Примеры настроек, влияющих на операции слияния:

* **Max bytes to merge at max space in pool**,
* **Merge max block size**,
* **Merge tree max bytes to use cache**.

### TTL {#ttl}

TTL (time to live) — это механизм, который ограничивает время жизни данных. По истечении заданного интервала времени можно автоматически удалять, перемещать или агрегировать строки и столбцы таблицы. Настроить перемещение строк с истекшим сроком жизни в объектное хранилище и задать значение TTL можно при [создании таблицы](../tutorials/hybrid-storage.md#create-table) или позднее.

При достаточном объеме свободного места в кластерном хранилище перемещение в объектное хранилище выполняется только для тех строк таблицы, для которых истекло значение TTL. Эта операция позволяет переместить часть данных в объектное хранилище, не дожидаясь заполнения кластерного хранилища.

Указывать TTL для использования гибридного хранилища необязательно, однако это позволяет явно контролировать, какие данные будут находиться в объектном хранилище. Если не указывать TTL, то данные будут помещаться в объектное хранилище, только когда в кластерном хранилище закончится место.

Данные перемещаются между кластерным и объектным хранилищами не построчно, а [кусками]({{ ch.docs }}{{ lang }}/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-multiple-volumes). Старайтесь выбирать выражение TTL и [ключ партиционирования]({{ ch.docs }}{{ lang }}/engines/table-engines/mergetree-family/custom-partitioning-key) так, чтобы для всех строк куска данных TTL совпадал. Если этого не сделать, то могут возникнуть проблемы с перемещением данных в объектное хранилище по истечении TTL, если один кусок будет содержать данные, предназначенные для разных уровней хранения. В самом простом случае выражение для TTL должно использовать те же столбцы, что и в ключе партиционирования.

Подробнее о настройке TTL читайте в [документации {{ CH }}]({{ ch.docs }}{{ lang }}/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-ttl).



## Выбор типа дисков при создании кластера {#storage-type-selection}

Количество хостов, которые можно создать вместе с кластером {{ CH }}, зависит от выбранного типа дисков:

* При использовании локальных SSD-дисков (`local-ssd`) вы можете создать кластер из двух или более хостов.

    Хранилище на локальных SSD-дисках влияет на тарификацию кластера: он тарифицируется, даже если остановлен. Подробнее в [правилах тарификации](../pricing.md).

* При использовании сетевых нереплицируемых SSD-дисков (`network-ssd-nonreplicated`) вы можете создать кластер из трех или более хостов.

* Вы можете добавить любое количество хостов в пределах текущей квоты при использовании следующих типов дисков:

    * сетевые HDD-диски (`network-hdd`);
    * сетевые SSD-диски (`network-ssd`);
    * сверхбыстрые сетевые SSD-диски с тремя репликами (`network-ssd-io-m3`).

Ограничения на количество хостов в кластере описаны в разделе [Квоты и лимиты](./limits.md).

## Управление дисковым пространством {#manage-storage-space}

В {{ mch-name }} при отсутствии свободного места в хранилище выполнение запросов на вставку (`INSERT`), фоновых мержей и мутаций приостанавливается. После [увеличения размера хранилища](../operations/update.md#change-disk-size) их выполнение возобновляется автоматически.


Для отслеживания степени заполнения хранилища [настройте алерты в {{ monitoring-full-name }}](../operations/monitoring.md#monitoring-integration).



### Автоматическое увеличение размера хранилища {#autoscaling}

Чтобы избежать ситуаций, когда свободное место на диске заканчивается и запросы на вставку, фоновые мержи и мутации перестают выполняться, настройте [автоматическое увеличение размера хранилища](../operations/update.md#change-additional-settings) для {{ CH }} и сервиса координации: {{ CK }} или {{ ZK }}. В этом случае хранилище увеличивается при достижении установленного порога срабатывания — процента от общего размера хранилища. Есть два порога:

* Порог для планового увеличения. Такое увеличение планируется по прогнозу алгоритма, который анализирует данные за последние несколько часов и оценивает, как быстро заполняется хранилище. Если расчеты показывают, что к началу ближайшего [окна обслуживания](maintenance.md#maintenance-window) заданный порог будет превышен, то планируется увеличение. Если проверка в начале обслуживания подтверждает, что заданный порог превышен, размер хранилища увеличивается.

* Порог для незамедлительного увеличения. При его достижении размер хранилища увеличивается немедленно.

Можно использовать один либо оба порога. Если заданы оба, порог для незамедлительного увеличения должен быть не меньше, чем для планового.

Для планового увеличения необходимо [настроить расписание окна обслуживания](../operations/cluster-maintenance.md#set-maintenance-window).

{% include [storage-resize-steps](../../_includes/mdb/mch/storage-resize-steps.md) %}

Настройки автоматического увеличения размера хранилища, заданные для {{ CH }}, применяются ко всем существующим шардам. При добавлении нового шарда значения настроек берутся с самого старого шарда.

Настроить автоматическое увеличение размера хранилища можно при [создании](../operations/cluster-create.md) или [изменении кластера](../operations/update.md#change-additional-settings).

{% note warning %}

* Размер хранилища нельзя уменьшить.
* Во время изменения размера хранилища хосты кластера будут недоступны.

{% endnote %}
