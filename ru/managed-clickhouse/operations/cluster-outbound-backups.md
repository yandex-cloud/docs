# Восстановление данных из резервной копии ch-backup

Если у вас есть выгрузка резервных копий кластера {{ mch-name }}, вы можете восстановить данные на своем сервере {{ CH }}. Для этого потребуются утилита [ch-backup](https://github.com/yandex/ch-backup) и доступ к S3-совместимому хранилищу с резервными копиями.

## Передаваемые данные {#data}

#|
|| **Ресурс** | **Содержимое** ||
|| Каталог резервных копий | Подкаталоги, каждый из которых соответствует одной резервной копии и назван ее именем. Внутри находятся файлы `backup_light_struct.json` с открытыми метаданными и `backup_struct.json` с зашифрованными полными метаданными, каталоги `metadata/` со схемами баз данных и таблиц, `data/` с кусками данных таблиц и `access_control/` с пользователями и ролями. ||
|#

Резервные копии дедуплицированы: если кусок данных не изменился, новая копия ссылается на него в одной из предыдущих копий. Для восстановления сохраните всю выгрузку, включая предыдущие резервные копии, на которые ссылается выбранная.

## Перед началом работы {#before-you-begin}

Для выполнения инструкции вам потребуются:

* Сервер с {{ CH }} той же или более новой версии, чем в исходном кластере. Версию исходного кластера можно узнать из [метаданных резервной копии](#inspect-backup). Примеры команд установки приведены для Ubuntu и Debian.
* Python 3.10 или выше для установки ch-backup. Запускайте ch-backup на том же сервере, где работает {{ CH }}: утилита записывает куски данных непосредственно в каталог данных сервера.
* Бакет в S3-совместимом хранилище, например в {{ objstorage-name }} или локальном MinIO. ch-backup читает резервные копии только из S3, восстановление непосредственно из локального каталога не поддерживается.
* Учетные данные с правами на чтение бакета. Если вы будете загружать выгрузку в бакет, потребуются также права на запись.
* Ключ шифрования резервных копий. Он отличается от статического ключа доступа к бакету.
* Свободное место на диске для восстановленных данных с запасом. Ориентируйтесь на значение `size` в выводе команды `ch-backup list -v` на этапе [проверки доступа](#check-access).

Для работы с метаданными установите `jq`:

```bash
sudo apt install -y jq
```

Для загрузки файлов в бакет установите и настройте [AWS CLI](../../storage/tools/aws-cli.md) для выбранного S3-совместимого хранилища.

## Восстановление данных {#restore}

### 1. Проверьте выгрузку {#inspect-backup}

В примерах ниже `/data/ch-dump` — локальный каталог с выгрузкой резервных копий. Найдите в нем файлы открытых метаданных:

```bash
find /data/ch-dump -name backup_light_struct.json
```

Пример результата:

```text
/data/ch-dump/ch_backup/c9qabcdefgh/shard1/b1/backup_light_struct.json
/data/ch-dump/ch_backup/c9qabcdefgh/shard1/b2/backup_light_struct.json
```

Каталог, содержащий подкаталоги резервных копий, — корень резервных копий. В примере это `ch_backup/c9qabcdefgh/shard1`. Этот путь понадобится при [настройке ch-backup](#configure-ch-backup).

Если корней несколько, например `shard1` и `shard2`, восстанавливайте каждый шард отдельно. Подробнее в разделе [Восстановление шардированного кластера](#sharded-cluster).

Если выгрузка уже находится в бакете, определите корень резервных копий по структуре объектов в бакете. Скачайте файл `backup_light_struct.json` выбранной копии, чтобы проверить его содержимое.

Посмотрите метаданные выбранной резервной копии. Если вы скачали файл из бакета, подставьте путь к скачанному файлу. Ключ шифрования для проверки не требуется:

```bash
jq -c '{name: .meta.name, state: .meta.state, ch_version: .meta.ch_version, start_time: .meta.start_time, s3_disks: .cloud_storage.disks}' \
  /data/ch-dump/<корень_резервных_копий>/<имя_резервной_копии>/backup_light_struct.json
```

Пример результата:

```json
{"name":"b2","state":"created","ch_version":"25.3.6.56","start_time":"2026-10-12 01:58:21.547967 +0000","s3_disks":[]}
```

Проверьте поля:

* `state` — должно иметь значение `created`. Другое значение означает, что резервная копия не завершена.
* `ch_version` — версия {{ CH }} исходного кластера.
* `s3_disks` — если список не пустой, в исходном кластере использовалось гибридное хранилище. Для восстановления холодных данных потребуется также копия бакета гибридного хранилища. Подробнее в разделе [Восстановление данных гибридного хранилища](#hybrid-storage).

### 2. Загрузите выгрузку в S3 {#upload-backup}

Если выгрузка уже находится в доступном вам бакете, переходите к [установке {{ CH }}](#install-clickhouse).

Загрузите всю выгрузку в S3-совместимый бакет с сохранением структуры каталогов. Префикс внутри бакета можно выбрать произвольно. Пример для {{ objstorage-name }}:

```bash
aws s3 mb s3://<имя_бакета> --endpoint-url https://{{ s3-storage-host }}
aws s3 sync /data/ch-dump s3://<имя_бакета>/<префикс> --endpoint-url https://{{ s3-storage-host }}
```

Если бакет уже создан, выполните только команду `aws s3 sync`. Для другого S3-совместимого хранилища укажите его эндпоинт в параметре `--endpoint-url`.

### 3. Установите {{ CH }} {#install-clickhouse}

Подключите [официальный репозиторий {{ CH }}](https://clickhouse.com/docs/install) и установите версию из поля `ch_version` или более новую:

```bash
sudo apt install -y clickhouse-server=<версия> clickhouse-client=<версия> clickhouse-common-static=<версия>
sudo systemctl start clickhouse-server
clickhouse-client -q "SELECT version()"
```

Используйте пустой сервер: на нем не должно быть пользовательских баз данных с теми же именами, что и в резервной копии.

Если при установке вы задали пароль пользователя `default`, передавайте его при подключении с помощью `clickhouse-client` и укажите в [конфигурации ch-backup](#configure-ch-backup).

### 4. Установите ch-backup {#install-ch-backup}

Соберите ch-backup из актуальной ветки `main` [репозитория](https://github.com/yandex/ch-backup):

```bash
sudo apt install -y curl git make python3-venv
curl -LsSf https://astral.sh/uv/install.sh | sh
. "$HOME/.local/bin/env"

git clone https://github.com/yandex/ch-backup.git
cd ch-backup
make build

sudo python3 -m venv /opt/ch-backup
sudo /opt/ch-backup/bin/pip install dist/ch_backup-*.whl
sudo ln -s /opt/ch-backup/bin/ch-backup /usr/local/bin/ch-backup
ch-backup --help
```

Для сборки используется `uv`. Команда `make build` создает пакет `dist/ch_backup-<версия>-py3-none-any.whl`, который устанавливается в виртуальное окружение Python.

В старых версиях ch-backup ссылки на дедуплицированные куски данных содержали полный путь. Такие ссылки могут перестать работать после изменения корня резервных копий.

### 5. Настройте ch-backup {#configure-ch-backup}

Создайте каталог конфигурации:

```bash
sudo mkdir -p /etc/yandex/ch-backup
```

Создайте в нем файл `ch-backup.conf`, который утилита читает по умолчанию:

```yaml
clickhouse:
  host: localhost
  # clickhouse_user: default
  # clickhouse_password: '<пароль_пользователя>'

backup:
  path_root: <префикс>/<корень_резервных_копий>

encryption:
  type: nacl
  key: '<ключ_шифрования>'

storage:
  type: s3
  credentials:
    endpoint_url: https://{{ s3-storage-host }}
    bucket: <имя_бакета>
    access_key_id: <идентификатор_статического_ключа>
    secret_access_key: '<секретный_ключ>'
  boto_config:
    region_name: {{ region-id }}
    addressing_style: path
```

Где:

* `clickhouse.host` — адрес локального сервера {{ CH }}. Если для подключения требуется пароль, раскомментируйте `clickhouse_user` и `clickhouse_password` и укажите учетные данные.
* `backup.path_root` — путь внутри бакета к каталогу, содержащему подкаталоги резервных копий, без имени бакета и имени конкретной копии. Например, `from-yc/ch_backup/c9qabcdefgh/shard1`. Если выгрузка расположена в корне бакета, не добавляйте префикс.
* `encryption.key` — содержимое файла ключа шифрования. Ключ должен занимать ровно 32 байта. Не добавляйте к нему пробелы или перевод строки из конца файла. Кавычки в примере — синтаксис YAML, они не входят в значение ключа.
* `storage.credentials` — эндпоинт, имя бакета и учетные данные для доступа к нему. В примере указан эндпоинт {{ objstorage-name }}; для другого хранилища замените его.
* `storage.boto_config.region_name` — регион S3-совместимого хранилища.
* `storage.boto_config.addressing_style: path` — способ адресации, подходящий для MinIO и большинства S3-совместимых хранилищ.

Ограничьте доступ к файлу конфигурации:

```bash
sudo chmod 600 /etc/yandex/ch-backup/ch-backup.conf
```

### 6. Проверьте доступ и ключ шифрования {#check-access}

Получите список резервных копий:

```bash
sudo ch-backup list -v
```

Пример результата:

```text
name    state    start_time                        end_time                             size    real_size  ch_version
------  -------  --------------------------------  --------------------------------  -------  -----------  ----------
b2      created  2026-10-12 01:58:21.547967 +0000  2026-10-12 01:58:23.914994 +0000  2149888       417792  25.3.6.56
b1      created  2026-10-12 01:58:16.744487 +0000  2026-10-12 01:58:19.526529 +0000  1732096      1732096  25.3.6.56
```

Если команда вернула список, доступ к бакету и `backup.path_root` настроены верно. Когда `real_size` меньше `size`, часть кусков данных находится в предыдущих резервных копиях.

Команда `list` читает открытые метаданные и не проверяет ключ шифрования. Для проверки расшифровки выполните:

```bash
sudo ch-backup show <имя_резервной_копии> | jq -r '.databases | keys[]'
```

Команда должна вывести список баз данных выбранной резервной копии.

### 7. Восстановите схемы и данные {#restore-data}

Если вы начинаете восстановление заново, например после очистки сервера, удалите файл состояния предыдущего восстановления:

```bash
sudo rm -f /tmp/ch_backup_restore_state.json
```

{% note warning %}

Если восстановление прервалось и вы хотите продолжить его, сохраните файл `/tmp/ch_backup_restore_state.json`. В нем ch-backup отмечает уже восстановленные куски данных. Если же сервер очищен, а файл состояния сохранен, утилита может пропустить отсутствующие куски данных и оставить таблицы пустыми.

{% endnote %}

Запустите восстановление:

```bash
sudo ch-backup restore <имя_резервной_копии> --force-non-replicated
```

Параметр `--force-non-replicated` преобразует таблицы семейства `Replicated*MergeTree` в соответствующие таблицы `*MergeTree`, а базы данных на движке `Replicated` — в базы на движке `Atomic`. Это позволяет восстановить данные на отдельном сервере без {{ ZK }} или {{ CK }}.

Дополнительные параметры:

* `-d db1,db2` — восстановить только указанные базы данных.
* `--exclude-databases db3` — исключить указанную базу данных из восстановления.
* `--table-included-patterns 'db1.orders,db2.*'` — восстановить только указанные таблицы.
* `--skip-cloud-storage` — пропустить холодные данные [гибридного хранилища](#hybrid-storage).
* `--keep-going` — продолжить восстановление, если отдельные таблицы не удалось восстановить. Проверьте ошибки в логе и полноту данных после завершения команды.

Подробный лог восстановления находится в файле `/var/log/ch-backup/ch-backup.log`.

### 8. Восстановите пользователей и роли {#restore-access}

Обычная команда `restore` не восстанавливает пользователей и роли. Выполните ее отдельно с параметром `--access`:

```bash
sudo ch-backup restore <имя_резервной_копии> --access
```

Пользователи, роли и права доступа, созданные через SQL, восстанавливаются вместе с хешами паролей. Существующие пароли продолжат работать. Пользователи, созданные средствами {{ mch-name }}, например через консоль управления или API, в резервную копию не попадают. Создайте их заново.

После восстановления:

* Проверьте список пользователей командой `SHOW USERS` и удалите или заблокируйте служебных пользователей исходного кластера.
* Настройте пароль пользователя `default` и сетевой доступ к серверу: `listen_host`, файрвол и TLS.

### 9. Проверьте данные {#verify-data}

Получите список восстановленных таблиц:

```bash
clickhouse-client -q "SELECT database, name, engine FROM system.tables WHERE database NOT IN ('system', 'INFORMATION_SCHEMA', 'information_schema')"
```

Проверьте количество строк в ключевых таблицах:

```bash
clickhouse-client -q "SELECT count() FROM <имя_базы_данных>.<имя_таблицы>"
```

Сравните результат с ожидаемым и проверьте работу приложения.

Таблицы на движке `Distributed` сохраняют ссылки на кластер из конфигурации исходного сервера (`remote_servers`). Настройте соответствующий кластер на новом сервере или пересоздайте таблицы под свою топологию. Если таблицы не нужны, удалите их. Пока конфигурация не настроена, запросы к таким таблицам будут завершаться ошибкой.

## Восстановление шардированного кластера {#sharded-cluster}

Для каждого шарда используется свой корень резервных копий. Восстанавливайте каждый шард на отдельный сервер {{ CH }}:

1. Установите {{ CH }} и ch-backup на сервер.
1. В параметре `backup.path_root` укажите корень резервных копий нужного шарда.
1. Повторите шаги [проверки доступа](#check-access), [восстановления данных](#restore-data), [пользователей](#restore-access) и [проверки результата](#verify-data).

В результате вы получите независимые серверы с частями данных. Их можно объединить в кластер с помощью таблиц `Distributed` или перенести данные на один сервер.

## Восстановление данных гибридного хранилища {#hybrid-storage}

Если в открытых метаданных резервной копии поле `s3_disks` не пустое, часть данных исходного кластера хранилась на S3-диске. В выгрузке резервных копий находятся метаданные этих кусков, а сами холодные данные остаются в отдельном бакете гибридного хранилища.

Без доступа к холодным данным восстановление может завершиться ошибкой `Cloud storage source bucket must be set if backup has data on S3 disks`.

Чтобы восстановить только данные с локальных дисков, используйте параметр `--skip-cloud-storage`:

```bash
sudo ch-backup restore <имя_резервной_копии> \
  --force-non-replicated \
  --skip-cloud-storage
```

{% note warning %}

При использовании `--skip-cloud-storage` холодные данные не восстанавливаются. Результат будет неполным.

{% endnote %}

Для восстановления холодных данных потребуется также копия бакета гибридного хранилища. Ее расположение задается параметрами `--cloud-storage-source-bucket`, `--cloud-storage-source-path` и `--cloud-storage-source-endpoint` команды `ch-backup restore`.

## Решение проблем {#troubleshooting}

#|
|| **Проблема** | **Что проверить** ||
|| Команда `list` возвращает пустой список. | Проверьте бакет и `backup.path_root`. Путь должен указывать на каталог, содержащий подкаталоги резервных копий. ||
|| `The key must be exactly 32 bytes long` | Проверьте длину ключа шифрования. В значение не должны попадать дополнительные пробелы, кавычки или перевод строки из конца файла. ||
|| `Failed to download backup metadata .../backup_struct.json` | Проверьте ключ шифрования: ошибка может означать, что полные метаданные не удалось расшифровать. Также проверьте наличие файла и доступ к нему. ||
|| `Connection refused` при подключении к порту `8123`. | Проверьте значение `clickhouse.host` и убедитесь, что сервер {{ CH }} запущен. ||
|| `Restore requires ZooKeeper or ClickHouse Keeper because we have replicated tables` | Для восстановления на отдельный сервер без сервиса координации добавьте параметр `--force-non-replicated`. ||
|#
