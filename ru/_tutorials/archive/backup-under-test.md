# Автоматическая проверка восстановления PostgreSQL и вложений в Object Storage

В этом руководстве вы создадите стенд, который восстанавливает Managed Service for PostgreSQL во временный кластер и проверяет соответствующие восстановленным записям версии файлов в Object Storage. После проверки стенд сохраняет отчет и удаляет временный кластер.

В учебном приложении заказы находятся в PostgreSQL, а документы — в бакете. В каждой записи сохраняются имя бакета, ключ объекта, идентификатор версии и SHA-256 содержимого. Благодаря этому после восстановления БД можно прочитать именно ту версию документа, которая соответствует заказу.

В ходе руководства вы воспроизведете два результата: успешную проверку после перезаписи текущей версии файла и ошибку после удаления версии, на которую ссылается восстановленная БД.

## Подготовьте окружение {#before-you-begin}

Понадобятся:

* Платежный аккаунт Yandex Cloud в состоянии `ACTIVE` или `TRIAL_ACTIVE` и привязанное к нему облако.
* Два отдельных пустых тестовых каталога: исходные ресурсы и ресурсы восстановления.
* Python 3.12+, Terraform 1.10+ и настроенный Yandex Cloud CLI.
* Исходный код примера из [репозитория](https://github.com/sonb54060-ctrl/docs/tree/2a30eb1304788333ac716a2d8e3415fb4c38e03d). Скачайте [архив проверенной версии](https://github.com/sonb54060-ctrl/docs/archive/2a30eb1304788333ac716a2d8e3415fb4c38e03d.zip), распакуйте его и откройте полученный каталог.
* Доступ оператора к созданию ресурсов и назначению перечисленных далее ролей в тестовых каталогах.
* Две свободные VPC-сети по квоте облака и шесть свободных подсетей. Если сеть `default` уже существует, квота сетей должна быть не менее трех.

В `operator_account_id` укажите IAM-идентификатор пользователя или сервисного аккаунта, от которого запускается Terraform. Политики бакетов явно сохраняют ему полный доступ к учебным бакетам. В Object Storage запрос, не совпавший ни с одним разрешающим правилом политики, отклоняется; одной дополнительной роли IAM недостаточно, чтобы исправить такое ограничение политики. Оператору также нужны права на создание и настройку бакетов, например `storage.admin` в тестовых каталогах.

Используйте только синтетические данные. Учебная функция отрицательного теста физически удаляет одну конкретную версию файла из учебного бакета.

### Необходимые платные ресурсы {#paid-resources}

В стоимость входят исходный PostgreSQL-кластер, временный кластер восстановления, хранение вложений и отчетов, операции Object Storage, вызовы Cloud Functions, выполнение Workflows, Lockbox и журналирование. В исходной конфигурации используются два vCPU, 8 ГБ RAM и SSD 10 ГБ на кластер; одновременно существует исходный кластер и не более одного штатного временного кластера.

Стоимость опыта оценивается по формуле:

`стоимость исходного кластера за время работы стенда + стоимость временного кластера за время его существования + хранение и операции сервисов`.

Сверьте [тарифы PostgreSQL](https://yandex.cloud/ru/docs/managed-postgresql/pricing), [Object Storage](https://yandex.cloud/ru/docs/storage/pricing), [Cloud Functions](https://yandex.cloud/ru/docs/functions/pricing) и [AI Studio](https://aistudio.yandex.ru/ru/docs/ai-studio/pricing).

Уборка временного кластера не удаляет исходный кластер, бакеты, секреты и накопленные резервные копии. Ошибка прав или API может задержать уборку: TTL не является жестким ограничителем расходов.

## Разверните основную инфраструктуру {#infrastructure}

Команды выполняются из корня исходного кода. Аутентифицируйте Terraform через поддерживаемый провайдером способ, например переменную `YC_TOKEN` с короткоживущим IAM-токеном текущего пользователя. Не записывайте токен в `.tfvars`.

1. Создайте виртуальное окружение Python, активируйте его и установите зависимости:

   ```sh
   python -m venv .venv
   python -m pip install -r requirements.txt
   python -m pip install -e ".[dev]"
   ```

   Между первой и второй командами активируйте окружение: в PowerShell — `./.venv/Scripts/Activate.ps1`, в Bash — `source .venv/bin/activate`.

2. Скопируйте `infra/base/terraform.tfvars.example` в `infra/base/terraform.tfvars`. Укажите идентификаторы облака и двух каталогов. При необходимости измените класс хоста.

3. Выполните:

   ```sh
   terraform -chdir=infra/base init -backend-config="path=<абсолютный-путь-вне-синхронизируемых-папок>/base.tfstate"
   terraform -chdir=infra/base plan -out=base.tfplan
   terraform -chdir=infra/base apply base.tfplan
   python scripts/export_outputs.py
   python scripts/package.py build/config.json
   ```

Исходный кластер и функции подготовки будут работать в одной VPC; временные кластеры и контроллер — в другой. Хосты БД не получают публичных IP-адресов. В обеих сетях создаются подсети в трех зонах доступности для подключения функций. Группы безопасности разрешают TCP 6432 из служебного диапазона Cloud Functions `198.19.0.0/16`: функции используют его, а не адреса пользовательских подсетей.

Terraform state содержит пароль учебной БД, поэтому его нужно хранить как секрет. Замените путь в команде `init` на существующий локальный каталог вне OneDrive, Dropbox и общих папок. Файлы планов также содержат секретные значения: если проект синхронизируется, укажите для `-out` и `apply` абсолютный путь в тот же закрытый каталог. В Git state, локальные `.tfvars`, файлы планов и каталог `build` не добавляются. S3-ключи создаются сразу в Lockbox с помощью `output_to_lockbox`.

### Разделение прав {#permissions}

* Аккаунт `setup` получает просмотр PostgreSQL в исходном каталоге, сетевой доступ, запись логов и разрешения бакета на работу с учебными файлами `demo/*`. Только эта функция может выполнять отрицательный тест.
* Аккаунт `controller` получает `managed-postgresql.restorer` в исходном каталоге и `managed-postgresql.editor` в каталоге восстановления. Доступ S3 ограничен чтением конкретных версий учебных вложений и работой с закрытым бакетом состояния и отчетов.
* Аккаунт `workflow` может вызывать контроллер и уборщик. Он не получает право вызывать функцию подготовки.
* Доступ к содержимому секретов Lockbox выдается соответствующим аккаунтам на конкретные секреты.
* Указанный в `operator_account_id` оператор сохраняет административный доступ к обоим учебным бакетам. Он необходим Terraform и для выгрузки отчетов и уборки; этот доступ не выдается функциям.

На бакете состояния аккаунтам `setup` и `controller` разрешен `ListBucket`, а на бакете вложений — аккаунту `controller`. Это позволяет различать отсутствующий объект и отказ в доступе. Содержимое вложений контроллер читает только через `GetObjectVersion` в `demo/*`.

Базовые IAM-роли назначаются на конкретные бакеты: `setup` получает `storage.editor` на вложениях, `controller` — `storage.viewer`; на бакете состояния оба получают `storage.editor`. После проверки IAM действует политика бакета, которая ограничивает перечисленные операции и ключи. Одна политика бакета без базового разрешения IAM/ACL не предоставляет доступ.

В учебных каталогах не должно быть сторонних баз. Каталожная роль редактирования PostgreSQL необходима для создания и удаления временного ресурса. Сам контроллер дополнительно проверяет каталог, идентификатор исходной БД и служебные метки перед удалением.

## Разверните автоматизацию {#automation}

Создайте `infra/automation/terraform.tfvars`:

```hcl
cloud_id              = "<идентификатор-облака>"
base_output_file      = "../../build/automation.json"
function_archive      = "../../build/function.zip"
enable_daily_schedule = false
```

Затем выполните:

```sh
terraform -chdir=infra/automation init -backend-config="path=<тот-же-закрытый-каталог>/automation.tfstate"
terraform -chdir=infra/automation plan -out=automation.tfplan
terraform -chdir=infra/automation apply automation.tfplan
terraform -chdir=infra/automation output
```

Будут созданы приватные функции `setup`, `controller`, `janitor`, процесс Workflows и таймер уборки раз в 15 минут. Ежедневное восстановление пока выключено.

Рабочий процесс обращается к коротким шагам контроллера в штатном цикле `While` и использует `Wait` между запросами статуса. Циклические переходы через `next` в YaWL запрещены. Функция не удерживается работающей все время восстановления. Workflows следует открывать в актуальном интерфейсе AI Studio.

## Подготовьте контрольную точку {#checkpoint}

1. Создайте десять синтетических заказов. Если вы изменили `lab_id`, замените `backup-lab` во всех командах подтверждения:

   ```sh
   python scripts/invoke.py setup seed --confirm backup-lab
   ```

   В каждую запись попадет идентификатор загруженной версии файла. Функция откажется перезаписывать уже заполненную таблицу.

2. Узнайте `source_cluster_id` из `build/config.json` и создайте ручную резервную копию:

   ```sh
   yc managed-postgresql cluster backup <source_cluster_id>
   yc managed-postgresql backup list --folder-id <source_folder_id>
   ```

3. Выберите созданную копию именно исходного кластера с типом `MANUAL` и статусом `DONE`. Убедитесь, что ее создание началось после заполнения таблицы. До окончания копирования не меняйте данные.

4. Зафиксируйте идентификатор:

   ```sh
   python scripts/invoke.py setup checkpoint --backup-id <backup_id>
   ```

Функция проверит, что копия принадлежит исходному кластеру, создана вручную, завершена и не началась раньше контрольных данных. Текущее содержимое таблицы должно совпадать с подготовленным набором.

Для ручной копии используется состояние на момент завершения ее создания. Произвольный PITR в этом опыте не применяется. Контрольная точка хранится в `control/checkpoint.json` и закрепляет конкретную резервную копию; расписание не подменяет ее автоматически.

## Проверьте восстановление после изменения данных {#positive-test}

1. Измените сумму одного заказа в исходной БД и перезапишите текущую версию его документа:

   ```sh
   python scripts/invoke.py setup mutate-order --confirm backup-lab
   python scripts/invoke.py setup overwrite --confirm backup-lab
   ```

2. В AI Studio откройте созданный Workflows и запустите его с входными данными:

   ```json
   {"run_id": "positive-001"}
   ```

3. Дождитесь завершения. Ожидаемый результат — `PASS` и `cleanup: CONFIRMED_ABSENT`.

4. В закрытом бакете, указанном как `control_bucket`, откройте или скачайте `reports/positive-001.html` и `reports/positive-001.json` через консоль Object Storage.

В отчете должны пройти проверки числа записей, суммы заказов, хеша набора и всех десяти вложений. Проверяется прежнее содержимое документа, потому что восстановленная запись содержит прежний `version_id`. Сумма заказа тоже должна соответствовать резервной копии, а не измененному источнику.

Можно дополнительно выполнить `python scripts/invoke.py setup delete-marker --confirm backup-lab` и запустить отдельный опыт `marker-001`. Обычный маркер удаления не уничтожает сохраненную версию, поэтому такой опыт также должен пройти.

Для пошаговой диагностики доступны команды `python scripts/invoke.py controller start --run-id debug-001` и `python scripts/invoke.py controller tick --run-id debug-001`. Повторяйте `tick` с интервалом не менее 30 секунд до `DONE` либо `MANUAL_REVIEW`. Это вспомогательный способ; основной запуск выполняет Workflows.

## Воспроизведите неполное восстановление {#negative-test}

{% note warning %}

Следующая команда безвозвратно удалит версию файла, на которую ссылается учебный заказ № 1. Выполняйте ее после успешного опыта и только в этом синтетическом стенде. После нее закрепленная контрольная точка останется непригодной для полного восстановления; обычная повторная загрузка файла создаст другой version_id.

{% endnote %}

1. Выполните:

   ```sh
   python scripts/invoke.py setup remove-version --confirm backup-lab
   ```

2. Запустите Workflows с новым идентификатором:

   ```json
   {"run_id": "negative-001"}
   ```

3. Ожидаемый результат процесса — ошибка, в итоговом отчете `result: FAIL`, а у `attachment:1` — `MISSING_VERSION`. Временный кластер при этом должен быть удален.

Именно этот опыт показывает, что успешного восстановления кластера недостаточно для подтверждения восстановления приложения. Оставшиеся девять документов должны пройти проверку.

Для нового положительного эксперимента разверните новый учебный набор/стенд и создайте новую контрольную точку. Не включайте ежедневные учения на заведомо поврежденной контрольной точке.

## Настройте расписание и наблюдение {#schedule}

На стенде с целой контрольной точкой задайте `enable_daily_schedule = true` в конфигурации автоматизации, просмотрите план и примените его. Процесс запускается ежедневно в 03:00 UTC. Имя ежедневного запуска содержит дату UTC, поэтому обычные повторные вызовы в тот же день не создают новый кластер.

В шаблоне используется проверенное API выражение `0 3 * * * *` для расписания Workflows. Таймер уборки использует API v2 (`yandex_serverless_triggers`) и отдельное выражение `*/15 * * * ? *`. Не переносите выражения между этими двумя настройками без проверки: при прохождении native schedule Workflows отклонил символ `?` и вариант с пятью полями.

Чтобы выключить расписание, дождитесь завершения активного опыта, задайте `enable_daily_schedule = false` и выполните `yc serverless workflow update <workflow_id> --remove-schedule`. Затем просмотрите и примените новый Terraform plan. Проверьте через `yc serverless workflow get <workflow_id> --format json`, что поле `schedule` отсутствует. В провайдере 0.228.0 это поле имеет семантику Optional+Computed: одного `false` недостаточно для надежного удаления уже установленного расписания. Облачный API также запрещает удалять Workflows, пока расписание существует. Явное снятие расписания сохраняет ID и историю процесса.

Таймер уборки работает независимо от процесса учений. Через два часа с начала восстановления ресурсы получают право на удаление уборщиком; проверка выполняется раз в 15 минут. Уборщик обрабатывает только совпадающие `managed-by`, `lab-id`, `source` и каталог восстановления. При ошибках API удаление не гарантируется: проверьте журнал и список кластеров.

Ход незавершенного опыта сохраняется в `runs/<run_id>.json` и `.html`, завершенный отчет — в `reports/<run_id>.json` и `.html`. Незавершенный опыт имеет `INCOMPLETE`, даже если проверки данных уже прошли. Не считайте его успешным до подтверждения уборки.

Настройте в используемой системе наблюдения уведомление о неуспешном Workflows и ошибках функции `janitor`. В пример входит структурированное журналирование; внешний канал уведомлений нужно подключить отдельно.

## Обработайте ошибки {#troubleshooting}

| Ситуация | Поведение и действия |
| --- | --- |
| Нет контрольной точки, копия не завершена | Восстановление не начинается; проверьте подготовку |
| Другой опыт уже активен | Новый запуск получает `BUSY`; дождитесь завершения первого |
| Файл недоступен по правам | Проверка возвращает `ACCESS_DENIED`; проверьте политику бакета и аккаунт контроллера |
| Нужная версия отсутствует | Проверка возвращает `MISSING_VERSION`; текущая версия не используется как замена |
| API отклонил создание по квоте | Итог `ERROR`; проверьте квоты и повторите с новым run_id |
| Ответ создания потерян | Контроллер ищет ресурс по меткам и не повторяет запрос создания |
| Исход операции неизвестен | `MANUAL_REVIEW`, новые запуски заблокированы; проверьте операции и все помеченные кластеры |
| Недостаточно прав для удаления | Опыт не станет успешным; исправьте права, вызовите `janitor` и проверьте фактическое отсутствие ресурса |
| Ошибка соединения с PostgreSQL | Проверьте CA, пароль, подсети функции, SG и наличие MASTER; подробности секретов в отчет не записываются |
| Network is not empty после удаления функций | Служебная очистка сети асинхронна. Проверьте `yc serverless network get-used <network_id>`, дождитесь `will_be_cleaned_up_at`, затем постройте новый план удаления оставшихся сетей. Не удаляйте записи из Terraform state вручную |

При `MANUAL_REVIEW` не удаляйте `control/active.json` автоматически. Неизвестный запрос может еще создать платный кластер. Сначала установите исход операции и убедитесь, что она завершена и ее ресурсы удалены. Сохраните текущее состояние для расследования; только после этого оператор может снять блокировку. Автоматическая уборка по меткам должна оставаться включенной до завершения разбирательства.

## Интерпретируйте время восстановления {#metrics}

`restore_seconds` — наблюдаемое время от отправки запроса восстановления до подтверждения завершения операции. Оно включает интервал опроса. `verification_seconds` — время чтения БД и проверки вложений. `cleanup_seconds` — наблюдаемое время уборки. Целевая проверка сравнивает время от начала восстановления до окончания прикладной проверки с заданным значением.

`recovered_data_age_seconds` показывает возраст подготовленных данных. Это не точное RPO. Для измерения потери подтвержденных операций нужен отдельный журнал контрольных транзакций. Результаты учебного кластера нельзя переносить на продуктивную нагрузку без испытаний с ее размером и характеристиками.

## Удалите учебные ресурсы {#cleanup}

1. Дождитесь окончания активного опыта, задайте `enable_daily_schedule = false` и выполните `yc serverless workflow update <workflow_id> --remove-schedule`, если расписание включалось. Просмотрите и примените новый план автоматизации. Убедитесь через API или консоль, что расписание отсутствует.
2. Проверьте каталог восстановления и отсутствие временных кластеров этого стенда. При необходимости запустите `python scripts/invoke.py janitor janitor` после исправления причины ошибки. Не отключайте уборщик, пока остаются незавершенные операции создания.
3. Сохраните нужные отчеты, затем удалите автоматизацию: `terraform -chdir=infra/automation destroy`.
4. В `infra/base/terraform.tfvars` задайте `source_deletion_protection = false`, проверьте план и примените его.
5. Через консоль Object Storage удалите учебные объекты, все их версии и маркеры удаления; сохраните необходимые отчеты перед очисткой второго бакета. Для автоматического удаления именно этих синтетических бакетов можно вместо ручной очистки задать `purge_synthetic_buckets = true` и применить план до следующего шага. Это разрешает безвозвратно удалить все объекты и версии в двух бакетах стенда; по умолчанию опция выключена.
6. После удаления функций запланируйте очистку их служебных подключений в обеих сетях: `yc serverless network trigger-used-cleanup <network_id>`. Используйте только идентификаторы сетей этого стенда. Команда возвращает `network_cleanup_time`: освобождение не мгновенное, в контрольном опыте оно было назначено примерно через 10 минут. Без принудительного запуска уборки служебные подсети могут удерживать сеть от 15 минут до 24 часов. Подробнее — [сеть Cloud Functions](https://yandex.cloud/ru/docs/functions/concepts/networking).
7. Выполните `terraform -chdir=infra/base destroy` и проверьте оставшиеся ресурсы. По [правилам Managed PostgreSQL](https://yandex.cloud/ru/docs/managed-postgresql/concepts/backup#storage) резервные копии удаленного кластера сохраняются еще 7 дней без тарификации, затем удаляются автоматически. Самостоятельно удалить их после удаления кластера нельзя. Не считайте такие копии оставленным работающим кластером и не повторяйте запросы удаления.
8. Функции и Workflows могут автоматически создать группу логов `default` в каждом тестовом каталоге. Сохраните нужные журналы, проверьте каталог группы и удалите именно эти учебные группы через `yc logging group delete <log_group_id>`.
9. Проверьте оба тестовых каталога и платежную детализацию. Удалите пустые каталоги, если создавали их только для опыта. Данные о расходах могут появляться с задержкой: пустая детализация сразу после удаления не означает нулевую стоимость.
