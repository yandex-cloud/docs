# Сводка характеристик системы

## Масштабируемость и производительность {#scalability-and-performance}

Пропускная способность {{ objstorage-onprem-name }} горизонтально масштабируется и зависит от:

- количества хостов, а следовательно:
    * дисков для данных;
    * сетевых интерфейсов;
    * копий Angel и Goose;
    * количества шардов s3db;
- количества дисков на одном хосте (вплоть до пропускной способности интерфейса дисковой полки);
- объема дисков: Angel параллельно записывает данные в бэкенды, пока не достигнет ограничения по IOPS самих дисков.

При вертикальном масштабировании производительность зависит от:

- производительности и числа ядер CPU — в первую очередь для обработки сетевых соединений и работы {{ PG }};
- объема и производительности RAM — для кеширования;
- производительности дисков для {{ PG }}, которая особенно важна;
- производительности дисков для Angel.

## Консистентность {#consistency}

Чтение данных из {{ objstorage-onprem-name }} консистентно: все изменения данных в S3 через один эндпоинт сразу видны через любой эндпоинт. Это обеспечивается алгоритмами слоя хранения MDS2 и взаимодействием Goose с {{ PG }}.

Слабая консистентность допустима только в двух случаях:

* Метаданные бакетов кешируются из реплик. Задержка их обновления зависит от обновления кешей и реплик {{ PG }}.
* Метаданные объектов могут быть прочитаны с реплики {{ PG }} в случае ошибок чтения с primary.

## Отказоустойчивость {#reliable-configurations}

Конфигурацию кластера выбирают с учетом зоны отказа:

- отдельного узла;
- стойки;
- или целого дата-центра.

Зона отказа выбирается при установке и влияет на топологию компонентов хранилища.

Рекомендуемая конфигурация рассчитана на отказ одной зоны и последующее восстановление избыточности. Она предусматривает размещение данных и компонентов в независимых зонах, а также запас ресурсов для восстановления после отказа.

Границы зон выбирают по общим зависимостям инфраструктуры: питанию, сети и размещению оборудования. Если несколько узлов используют общее питание стойки, размещение копий на разных узлах не защищает от отказа этой стойки. Аналогично, распределение по стойкам одного дата-центра не защищает от отказа всего дата-центра.

{% note info %}

Зоны отказа задаются логически.

Несколько зон отказа нельзя разместить на одном узле, но можно разместить в одной стойке или одном ДЦ.

Это позволяет развернуть хранилище в меньшем количестве стоек или ДЦ (вплоть до одного), но отказ одной физической зоны может привести к отказу нескольких логических.

{% endnote %}

Чтобы чтение и запись оставались доступны, должны работать MDS2, базы данных и сервисы, обслуживающие запросы. У оставшихся компонентов должны сохраняться необходимые кворумы, сетевая доступность и ресурсы для обработки нагрузки.

### Размещение и отказы {#placement-and-failures}

*Устойчивость к отказам зависит от схемы избыточности и физического размещения частей контейнера*. Несколько частей на одном сервере становятся недоступны одновременно при отказе этого сервера.

EC допускает использование менее `D+P` серверов, однако такое размещение снижает устойчивость к отказам. Например, EC 4+2 можно использовать и в кластере из 6 серверов, так и в кластере из трех, разместив по две части контейнера на каждом:

* при размещении по две части на трех серверах отказ одного сервера оставляет четыре части — достаточно для восстановления данных;

* при размещении по одной части на шести серверах четыре части остаются после отказа двух серверов.

### Доступность при отказе одной зоны {#single-zone-failure}

Для доступности чтения и записи необходимы:

* не менее трех зон: узлов, стоек или дата-центров — в зависимости от выбранной зоны отказа;

* достаточная избыточность данных, например:

    * репликация x3 с размещением копий в разных зонах;
    * либо EC 4+2 с размещением не более двух частей одного контейнера в каждой зоне;

* три экземпляра каждого кластера {{ PG }} — primary и две реплики — в разных зонах.

Отказ одной зоны приводит к потере одного экземпляра {{ PG }} и трети частей контейнеров. Оставшихся компонентов достаточно для продолжения чтения и записи.

### Восстановление избыточности {#redundancy-recovery}

Чтобы после отказа одной зоны восстановить исходную избыточность, не дожидаясь ее возвращения, нужны как минимум четыре зоны и достаточные свободные ресурсы. Это позволяет разместить новые копии данных и экземпляры компонентов в трех оставшихся зонах, сохранив требования к их разделению. Например, после отказа первой зоны новые экземпляры {{ PG }} и части контейнеров с репликацией x3 будут размещены в четвертой зоне (при наличии ресурсов).

В конфигурации из трех зон полное восстановление исходной схемы размещения требует возвращения отказавшей зоны или добавления новой. До этого система работает с пониженным запасом избыточности.

Например, в одной зоне нельзя размещать больше двух частей контейнера EC 4+2: при отказе этой зоны часть данных станет недоступна для чтения.

### Доступность при отказе двух зон {#two-zone-failure}

Последствия отказа двух зон зависят от размещения данных и от того, произошли отказы одновременно или между ними система успела восстановить избыточность.

При *одновременном* отказе двух зон для репликации x3:

* *В конфигурации из трех зон* у каждого контейнера остается одна копия данных, а у каждого кластера {{ PG }} — один экземпляр. Кворума для записи в MDS2 недостаточно. Чтение возможно для объектов, данные и метаданные которых сохранились в оставшейся зоне. Последние подтвержденные изменения могли еще не попасть на оставшиеся экземпляры, поэтому доступность чтения всех объектов и актуальность ответов не гарантируются.

* *В конфигурации из четырех и более зон* часть контейнеров и кластеров {{ PG }} может потерять только одного участника и сохранить возможность записи. Остальные потеряют двух участников. Поэтому запись может оставаться доступной для части запросов — в зависимости от размещения данных и состояния необходимых кластеров {{ PG }}. Чтение сохранившихся объектов возможно с теми же ограничениями, что и в конфигурации из трех зон.

Для EC 4+2 возможность чтения закодированных данных определяется числом сохранившихся частей: нужны как минимум четыре.

{% note info %}

Одновременный отказ двух независимых зон выходит за рамки рекомендуемой модели отказов.

Этот сценарий показывает ограничения системы. Если при таком отказе требуется сохранять полную доступность, конфигурацию проектируют отдельно.

{% endnote %}

При *последовательных* отказах результат зависит от завершения восстановления. Если после первого отказа в конфигурации из четырех зон система успела восстановить избыточность MDS2 и состав кластеров {{ PG }} в трех оставшихся зонах, следующий отказ снова *соответствует потере одной зоны* относительно восстановленного размещения.

Для этого нужны достаточные свободные ресурсы, подходящее размещение и время на восстановление.

### Сохранность данных при полной потере питания {#power-loss}

Потеря питания в одной зоне соответствует [сценарию отказа одной зоны](#single-zone-failure). Ниже описано, что происходит при одновременном отключении питания всего хранилища.

Все компоненты, отвечающие за сохранение метаданных, выполняют `fsync` перед подтверждением записи. Поэтому после восстановления питания все метаданные будут доступны.

По умолчанию для подтверждения записи самих данных не требуется `fsync`: Angel выполняет принудительный `fsync` периодически и по мере достижения настроенного объема записи. Это позволяет поддерживать производительность.

Если питание одновременно теряют все участники, содержащие последние записи, часть уже подтвержденных данных может быть потеряна. Это возможно:

- при отказе питания стойки, если все узлы хранилища расположены в одной стойке;
- или отказе питания в дата-центре, если все узлы расположены в одном дата-центре.

Частоту `fsync` можно настроить. Более частая синхронизация сокращает окно возможной потери данных (RPO), но увеличивает нагрузку на диски и снижает производительность записи.
