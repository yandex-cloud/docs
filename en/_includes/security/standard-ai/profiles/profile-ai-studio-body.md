{#profile-ai-studio-applicability}

**Scope and status**

This profile is applied to the managed [{{ ai-studio-name }} API]({{ link-docs-ai }}ai-studio/concepts/api). In the architecture, a specific capability is identified, such as text generation, Responses, Realtime, or another documented API operation. Guardrails and {{ iam-short-name }} access policies only count for actual usage; both features are documented as being at the Preview stage and require a separate availability check.

{#profile-ai-studio-flow}

**Flow and trust boundaries**

`user → application or runtime environment → {{ ai-studio-name }} API → model → application`. The input and response cross the application validation boundary; files, responses, and guardrails form separate branches.

{#profile-ai-studio-authentication}

**Workload identity and authentication**

The runtime environment uses a separate service account and an IAM token or API key documented for the selected API. Managing the MCP Hub requires an IAM token rather than an API key. The methods and headers are listed in the [authentication guides]({{ link-docs-ai }}ai-studio/api-ref/authentication.html).

{#profile-ai-studio-roles}

**Roles and scope**

For text generation, `ai.languageModels.user` is checked; for Responses, `ai.assistants.editor` together with `ai.languageModels.user`; for Realtime, `ai.models.user`. Assignments are checked at the supported organization, cloud, or catalog level. The role from one API does not transfer to another; role semantics are derived from the [{{ ai-studio-name }} access model]({{ link-docs-ai }}ai-studio/security/index.html).

{#profile-ai-studio-network}

**Network**

The actual managed endpoint and runtime source path are recorded. If the [{{ iam-short-name }} access policy](../../../../iam/concepts/access-control/access-policies.md) is used for Responses, the `aistudio.responses.restrictNetworkAccess`, `allowed_src_ips`, `allowed_vpc_network_ids` pattern and the allowed and denied sources are checked. This policy restricts a previously granted permission and does not create a private endpoint.

{#profile-ai-studio-secrets}

**Secrets and credentials**

For an API key, the following are recorded: ID, owner service account, scopes, expiration or review date, and delivery path from the runtime environment profile. The key value is not included in the configuration record. For an IAM token, the workload identity and acquisition method are logged.

{#profile-ai-studio-configuration}

**Configuration objects**

Catalog ID, model and API capability, service account, bindings, API key ID and scopes, application configuration version; where applicable, guardrail ID and version and {{ iam-short-name }} access policy.

{#profile-ai-studio-telemetry}

**Telemetry and blind spots**

Only published [{{ at-name }} events for {{ ai-studio-name }} are used]({{ link-docs-ai }}ai-studio/at-ref.html). They do not guarantee a full prompt, response, or end-to-end application correlation; the missing trace is generated by the application. Export and analysis are configured in line with the [official guide]({{ link-docs-ai }}ai-studio/operations/security/analyze-logs.html).

{#profile-ai-studio-checks}

**Positive and negative checks**

1. Make an authorized invocation. Check the following: rejection due to a missing role, rejection due to a revoked or unsuitable key, and correlation with the application record.
1. For the {{ iam-short-name }} access policy, check the allowed and denied network sources.
1. For guardrails, check the allowed category, blocking, and moderator error.

{#profile-ai-studio-inputs}

**What you need for profile implementation**

* Architecture: API, model, runtime environment, and data branches.
* Policy: IAM token or API key, key expiration, network restrictions, and log rules and composition.
* Legal approach: permissible data categories, target, recipients, and retention period.
