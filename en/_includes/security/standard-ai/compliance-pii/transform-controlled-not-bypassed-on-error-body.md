{#ai-comply-pii3-id}

Requirement ID: `AI-COMPLY-PII3`

{#ai-comply-pii3-applicability}

**Scope**

The requirement applies if one of the following is implemented for the scenario: software-based masking, tokenization, pseudonymization, detokenization, or another protective transformation.

{#ai-comply-pii3-risk}

**Risk**

Unauthorized de-anonymization, substitution of rules, key compromise, or emergency bypass of the transformation process can lead to disclosure of regulated data.

{#ai-comply-pii3-requirement}

**Requirement**

Access to modifying algorithms and rules, reading verification records, using keys and mapping tables, and performing reverse transformation must be granted based on the principles of least privilege and separation of duties.

A masking, tokenization, pseudonymization, detokenization event or another protective transformation is generated by an application or transformation component. {{ cloud-logging-name }} only accepts this event. {{ at-name }} records published cloud operations but does not acknowledge the execution of each individual application-level transformation operation. For each forward and inverse transformation operation, the following must be recorded:

* Time and technical request ID.
* Component, service account, or user.
* ID and version of the applied rule.
* Type of operation and technical result.
* Indication of an error, failure, or explicitly permitted exception.

Source personal data, keys, and mapping tables must not be included in logs without separate justification, approval, and protective measures.

A parser error, unknown field, corrupted input, or converter unavailability must not result in the model's source data being sent to an external recipient or a technical log; acceptable failure behavior is defined alongside the processing policy. Any subsequent call to a model, RAG, tool, or log must only receive the converter's typed, successful output; a bypass, timeout, exception, or invalid result will block the call.

Read permissions for the logs in {{ cloud-logging-name }} and {{ at-name }} must also be restricted.

{#ai-comply-pii3-recommendation}

**Recommendation**

Export required audit events to {{ yandex-siem-full-name }}, set retention periods for records, protect it against unauthorized alteration, and regularly review access to it. {{ yandex-cloud }} documentation also recommends analyzing {{ cloud-logging-name }} and {{ at-name }} when investigating a compromise of secrets.

{#ai-comply-pii3-check}

**Check**

1. Perform a successful transformation using synthetic data and check how the following are handled: input with an unknown field, a corrupted object, and converter unavailability.
1. Verify the failure before crossing the trust boundary in all error scenarios.
1. Check for an attempted bypass via an alternative API, queue, log, or administrative interface.
1. Verify the denial of the reverse transformation to an unauthorized subject.
1. Confirm that the evidence contains time, component, rule version, operation type, and error or bypass indicator – without source values, keys, or mapping tables.
1. Make sure the subject who modifies the rule does not get the permission to perform detokenization and modify or read evidence without a separate, approved exception at the same time.

{#ai-comply-pii3-artifacts}

**Artifact**

* IAM policies and role models.
* {{ at-name }} and {{ cloud-logging-name }} configuration.
* Transformation logs.
* Rejection logs.
* Fault tolerance test results.
* Rules for storage and access to evidence.
* Event schema.
* Unavailability and bypass tests.
