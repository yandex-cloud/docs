# Обновить кластер

Обновите кластер Stackland до новой версии с помощью ресурса Kubernetes `TargetInstallationState`. Обновление выполняется постепенно с эвакуацией нагрузки и перезагрузкой узлов.

## Перед началом работы {#before-you-begin}

1. Убедитесь, что у вас есть доступ к кластеру с правами администратора.
1. Проверьте текущую версию кластера:

    ```bash
    kubectl get targetinstallationstate main -o jsonpath='{.status.currentVersion}'
    ```

1. Узнайте, какие версии доступны для обновления. Список доступных версий зависит от того, подключен ли ваш кластер к интернету:

    * **Кластер с доступом в интернет** — доступные версии загружаются автоматически из реестра контейнеров Stackland.
    * **Изолированный кластер** — доступные версии определяются образами, загруженными в локальный реестр.

## Настроить Cilium для gVisor и Kata {#cilium-socket-lb}

Начиная с версии 26.3.2, sladm по умолчанию включает `hostNamespaceOnly` при установке, обновлении или масштабировании кластера, если в итоговых `features` хотя бы одного узла есть `gvisor` или `kata` с учётом наследования. Если поле не задано или равно `null`, действует автоматический выбор; явные `true` и `false` имеют приоритет. Без gVisor и Kata настройка по умолчанию выключена.

Настройка общая для всех узлов. Она позволяет подам, запущенным с gVisor или Kata Containers, обращаться к ClusterIP, включая DNS.

Чтобы включить настройку явно, добавьте в конфигурацию кластера:

```yaml
spec:
  cluster:
    networking:
      cilium:
        socketLB:
          hostNamespaceOnly: true
```

1. Убедитесь, что целевой релиз поддерживает это поле. До перехода на такой релиз не запускайте масштабирование с новым полем: старый sladm отвергнет конфигурацию.
1. Откройте ConfigMap и добавьте поле в YAML ключа `cluster.yaml`:

    ```bash
    kubectl -n stackland-install edit configmap stackland-cluster-config
    ```

1. Запустите обновление кластера по инструкции ниже. Если поддерживающая поле версия уже установлена, настройка применится и при следующем масштабировании. Повторное применение обновления на той же версии не запускает sladm.

При изменении значения sladm обновляет `cilium-config` и перезапускает cilium-agent на всех нодах. Чтобы выключить настройку, явно задайте `false`, затем выполните обновление или масштабирование. Удаление поля `hostNamespaceOnly` возвращает автоматический выбор по `features`: при наличии gVisor или Kata настройка будет включена. Изменяйте только `socketLB`, сохраняя другие настройки `cilium`, в том числе `resources`.

{% note warning %}

При выключении соединения к ClusterIP, открытые в этом режиме, рвутся: TCP требует переподключения, connected UDP-сокеты не восстанавливаются. Перезапустите поды с долгоживущими соединениями.

При `true` поды теряют защиту Cilium от CVE-2020-8554: не разрешайте тенантам создавать Service с `spec.externalIPs`. Если под обращается к Service, за которым стоит он сам, источник запроса меняется на `169.254.42.1`.

{% endnote %}

## Настроить память Cilium {#cilium-memory}

В `spec.cluster.networking.cilium.resources` можно независимо задать `requests.memory` и `limits.memory` для cilium-agent. Оба поля необязательны и принимают строки с положительными Kubernetes quantities, например `"512Mi"` или `"2G"`. Отсутствующее поле или `null` использует встроенное значение запускаемого релиза sladm: в текущем релизе это **256Mi request / 4Gi limit**. После подстановки значений по умолчанию request должен быть не больше limit; неверную пару sladm отклоняет до обращения к Helm.

Пример синтаксиса ниже задаёт request `512Mi` и limit `8Gi`. Подберите значения под нагрузку и доступную память своих нод: пример не является универсальной рекомендацией по размеру памяти.

```yaml
spec:
  cluster:
    networking:
      cilium:
        resources:
          requests:
            memory: "512Mi"
          limits:
            memory: "8Gi"
```

Настройки общие для всех нод. Увеличенный request учитывается планировщиком и может помешать размещению cilium-agent на нодах с меньшим объёмом доступной памяти. Повышение limit не требует такого же повышения request. Автоматического подбора памяти нет; размеры BPF maps и существующая привязка `GOMEMLIMIT` к `limits.memory` сохраняются.

Убедитесь, что запускаемый релиз поддерживает `resources`; до обновления на такой релиз не запускайте resize с новыми полями. Для новой установки добавьте поля в исходный установочный конфиг.

На работающем кластере дождитесь завершения текущего запуска sladm перед редактированием: он записывает свой прочитанный конфиг обратно и может затереть одновременные правки. Затем измените YAML в ключе `cluster.yaml` ConfigMap `stackland-install/stackland-cluster-config`:

```bash
kubectl -n stackland-install edit configmap stackland-cluster-config
```

sladm применяет настройки при install, upgrade и resize. Само изменение ConfigMap не запускает применение; повторный запрос уже завершённого обновления на ту же версию тоже не перезапускает sladm. После правки выполните поддерживаемое обновление или масштабирование. Изменение эффективных ресурсов меняет шаблон DaemonSet и запускает rollout cilium-agent по нодам; дождитесь его завершения.

Чтобы сбросить отдельную настройку, удалите соответствующее поле `memory` или задайте ему `null`. При следующем запуске sladm восстановит встроенное значение своего релиза и явно заменит прежнее значение в Helm, даже при повторном использовании Helm values. Лимит при этом остаётся заданным, а старый override не сохраняется. Исходный YAML не дополняется вычисленными значениями. Сохраняйте остальные настройки, включая `socketLB`.

Перед запуском старого sladm, который не поддерживает эти поля, вручную удалите блок `resources` и другие неподдерживаемые поля из входного конфига: иначе строгий парсер отклонит его. Заранее проверьте, достаточно ли памяти по умолчанию в целевом старом релизе — его значения могут отличаться от 256Mi/4Gi. Выбранные overrides при удалении теряются, и OOM может повториться; если старых значений недостаточно, одного удаления полей для отката недостаточно. Совместимость обеспечивается этой ручной подготовкой: backport и автоматическое преобразование конфигурации не предусмотрены.

## Выбрать релизный канал {#release-channel}

Релизный канал определяет, какие версии Stackland доступны для обновления. По умолчанию используется канал `stable`.

Доступные каналы:

* `stable` — стабильные релизы для production-использования. Доступен всем клиентам по умолчанию.
* `alpha` — ранние релизы для тестирования новых функций. Доступ предоставляется по запросу.

Чтобы изменить релизный канал, отредактируйте ресурс `PlatformConfig`:

```bash
kubectl edit platformconfig main
```

В спецификации укажите нужный канал:

```yaml
spec:
  releaseChannel: "stable"  # или "alpha"
```

## Подготовить Object Storage к обновлению на 26.4 и выше {#storage-postgresql-upgrade}

Если в кластере используется Object Storage с метабазой PostgreSQL 15, перед обновлением Stackland на версию 26.4.0 или выше переведите метабазу на PostgreSQL 17. В версии 26.3 можно продолжать использовать PostgreSQL 15. Для новых установок Object Storage PostgreSQL 17 включен автоматически.

{% note warning %}

Во время обновления метабазы S3 API недоступен. Выберите время обслуживания с учетом приложений, которые используют Object Storage. Обновление метабазы начинается после явного подтверждения администратора.

{% endnote %}

1. Если обновление кластера уже запрошено, проверьте причину блокировки:

    ```bash
    kubectl get targetinstallationstate main -o yaml
    ```

    Если требуется обновить метабазу, ресурс переходит в `status.phase: Blocked`, а в `status.message` появляется сообщение о необходимости PostgreSQL 17.

1. В выбранное время обслуживания подтвердите обновление метабазы:

    ```bash
    kubectl annotate storageconfig main \
      stackland.yandex.cloud/approve-postgres-upgrade=true --overwrite
    ```

1. Отслеживайте состояние Object Storage:

    ```bash
    kubectl get storageconfig main -o yaml
    ```

    После успешного обновления хранилище возвращается в `Ready`, а аннотация подтверждения удаляется автоматически. Проверьте доступ приложений к S3 API. Если обновление кластера было заблокировано из-за версии метабазы, оно продолжится автоматически.

## Перед обновлением на 27.x {#pre-upgrade-27}

В Stackland 26.2 добавлена новая реализация Ingress-контроллера на основе Contour: предыдущая реализация на базе ingress-nginx больше не поддерживается. В Stackland 27 ingress-nginx будет исключен из поставки, поэтому мы предупреждаем вас об этих планах заранее. В релизах Stackland 26 ingress-nginx по-прежнему доступен для пользовательской нагрузки, но переход на новую реализацию нужно запланировать и осуществить до обновления на Stackland 27.

В большинстве случаев пользовательские манифесты `Ingress` с классом `stackland-default` продолжают работать, но специфичные для ingress-nginx аннотации `nginx.ingress.kubernetes.io/*` новый контроллер не поддерживает — их нужно убрать или заменить. Подробнее см. в разделе [Проверить пользовательские ресурсы Ingress](#check-user-ingress).

При этом действие оператора обязательно: без явного отключения предыдущей реализации Ingress-контроллера обновление на версию `>= 27.0.0` не начнется.

### Проверить пользовательские ресурсы Ingress {#check-user-ingress}

Если в кластере есть пользовательские ресурсы `Ingress`:

1. Найдите пользовательские ресурсы `Ingress`:

    ```bash
    kubectl get ingress -A
    ```

1. Убедитесь, что у них указан `spec.ingressClassName: stackland-default` или поле отсутствует. В последнем случае используется класс по умолчанию.
1. Проверьте, что в аннотациях не используются ключи вида `nginx.ingress.kubernetes.io/*`, специфичные для nginx. Если такие аннотации есть, уберите их или замените на эквиваленты нового Ingress-контроллера платформы — иначе после обновления соответствующие правила не применятся.

### Проверить работу приложения заранее {#test-before-upgrade}

Пока кластер работает на 26.x, вы можете заранее убедиться, что пользовательский `Ingress` совместим с новым Ingress-контроллером платформы.

{% note warning %}

При переключении `spec.ingressClassName` на `stackland-system` учитывайте, что у класса `stackland-system` собственный внешний IP-адрес, отличный от IP-адреса предыдущей реализации. Если DNS-зона делегирована платформе, запись домена автоматически переедет на LoadBalancer нового класса, но с задержкой на обновление DNS-записей — на это время часть клиентов будет обращаться по прежнему IP-адресу и попадать на предыдущую реализацию Ingress. После возврата класса на `stackland-default` действует аналогичная задержка.

Выполняйте проверку в окне технического обслуживания или на некритичном хосте.

{% endnote %}

1. Во временной копии манифеста замените `spec.ingressClassName: stackland-default` на `spec.ingressClassName: stackland-system` и примените манифест:

    ```bash
    kubectl apply -f <имя_файла>.yaml
    ```

1. Проверьте доступность приложения. Есть два способа:

    * Проверка напрямую через IP, без DNS. Этот способ не зависит от DNS-пропагации и от размещения DNS-зоны домена приложения.

        1. Получите внешний IP LoadBalancer, обслуживающего класс `stackland-system`:

            ```bash
            kubectl get svc -A \
              -l app.kubernetes.io/name=contour,app.kubernetes.io/component=envoy
            ```

            Если селектор не подходит для вашей установки, найдите сервис типа `LoadBalancer` в неймспейсе Contour вручную.

        1. Выполните запрос к приложению, подставив полученный IP:

            ```bash
            curl --resolve <домен>:443:<внешний_IP_Envoy> https://<домен>/
            ```

    * Проверка по домену. Работает, только если DNS-зона делегирована — тогда запись домена переместится на LoadBalancer класса `stackland-system` автоматически. Учитывайте задержку DNS. Если вы используете свой DNS, домен продолжит указывать на предыдущий LoadBalancer, и такая проверка даст ложно-отрицательный результат — используйте способ с `curl --resolve`.

1. После проверки верните значение `spec.ingressClassName` обратно на `stackland-default` или удалите поле.

На 27.x этот шаг не нужен: класс `stackland-default` автоматически обслуживается новым Ingress-контроллером платформы.

{% note warning %}

`stackland-system` — служебный класс. Не используйте его для production-ресурсов `Ingress`, это только способ временной проверки совместимости перед обновлением.

{% endnote %}

### Отключить предыдущую реализацию Ingress {#disable-legacy-ingress}

1. Отключите предыдущую реализацию Ingress в ресурсе `IngressConfig`:

    ```bash
    kubectl patch ingressconfig main --type=merge \
      -p '{"spec":{"settings":{"nginx":{"enabled":false}}}}'
    ```

  После отключения ingress-nginx существующие Ingress-контроллеры будут автоматически перезапущены поверх Contour.

1. Дождитесь, пока платформа переключится на единый Ingress-контроллер. Проверьте текущее состояние:

    ```bash
    kubectl get ingressconfig main -o jsonpath='{.status.ingress.observedIngress}'
    ```

- CLI {#cli}

  Инструкции CLI зависят от того, имеет ли кластер доступ в интернет.

    ### Кластер с доступом в интернет {#online-cluster}

    Если кластер имеет доступ в интернет, образы новой версии загружаются автоматически из реестра контейнеров Stackland.

    #### Подготовка к обновлению {#prepare-online}

    Дождитесь появления нового релиза в ресурсе `AvailableReleases`. Проверить доступные релизы можно командой:

    ```bash
    kubectl get availablereleases main -o yaml
    ```

    Пример вывода:

    ```yaml
    apiVersion: stackland.yandex.cloud/v1alpha1
    kind: AvailableReleases
    metadata:
      name: main
    status:
      releases:
        - version: "26.1.0"
          ready: true
        - version: "26.1.1"
          ready: true
    ```

    Когда нужная версия появится в списке со статусом `ready: true`, можно запускать обновление.

    #### Запустить обновление {#start-upgrade-online}

    1. Создайте файл манифеста. Например, с помощью команды `touch upgrade.yaml`.
    1. Откройте файл и вставьте конфигурацию:

        ```yaml
        apiVersion: stackland.yandex.cloud/v1alpha1
        kind: TargetInstallationState
        metadata:
          name: main
        spec:
          targetVersion: "<версия>"
          installationTimeout: "2h"
        ```

        Где:
        * `targetVersion` — целевая версия для обновления. Укажите значение из `availablereleases[main].status.releases[<желаемый_релиз>].version`.
        * `installationTimeout` — максимальное время выполнения обновления.

    1. Примените манифест:

        ```bash
        kubectl apply -f upgrade.yaml
        ```

  ### Изолированный кластер {#airgapped-cluster}

    Если кластер не имеет доступа в интернет, необходимо предварительно загрузить образы новой версии в локальный реестр.

    #### Скачать утилиту SLADM {#download-sladm}

    На машине с доступом в интернет скачайте свежую версию утилиты `sladm`, как при первоначальной установке.

    #### Загрузить образы на машине с интернетом {#download-images}

    На машине с доступом в интернет выполните команду:

    ```bash
    sladm pull --image-bundle full
    ```

    Где:
    * `--image-bundle` — тип пакета образов (`full` для полного набора).

    {% note info %}

    Для обновления образов отдельно лицензируемых компонентов, таких как SpeechSense, дополнительно выполните загрузку с `--image-bundle speechsense`. Подробнее см. в разделе [Загрузить образы SpeechSense](../speechsense/install-images.md).

    {% endnote %}

    #### Перенести артефакты во внутренний контур {#transfer-artifacts}

    Перенесите на машину с доступом к локальному реестру кластера:

    * бинарный файл `sladm`;
    * файл `release.yaml`;
    * папку `<имя_релиза>-oci`.

    #### Загрузить образы в локальный реестр {#push-images}

    На машине с доступом к кластеру выполните команду:

    ```bash
    sladm push --local-registry --kubeconfig=<путь_к_kubeconfig> --image-bundle-folder <имя_папки>-oci
    ```

    Где:

    * `--local-registry` — указывает на использование локального реестра кластера;
    * `--kubeconfig` — путь к файлу kubeconfig для доступа к кластеру;
    * `--image-bundle-folder` — путь к папке с образами.

    #### Дождаться появления релиза {#wait-for-release}

    После загрузки образов дождитесь появления нового релиза в ресурсе `AvailableReleases`:

    ```bash
    kubectl get availablereleases main -o yaml
    ```

    Когда нужная версия появится в списке со статусом `ready: true`, можно запускать обновление.

    #### Запустить обновление {#start-upgrade-offline}

    1. Создайте файл манифеста. Например, с помощью команды `touch upgrade.yaml`.
    1. Откройте файл и вставьте конфигурацию:

        ```yaml
        apiVersion: stackland.yandex.cloud/v1alpha1
        kind: TargetInstallationState
        metadata:
          name: main
        spec:
          targetVersion: "<версия>"
          installationTimeout: "2h"
        ```

        Где:
        * `targetVersion` — целевая версия для обновления. Укажите значение из `availablereleases[main].status.releases[<желаемый_релиз>].version`.
        * `installationTimeout` — максимальное время выполнения обновления.

    1. Примените манифест:

        ```bash
        kubectl apply -f upgrade.yaml
        ```

## Проверить статус обновления {#check-status}

После применения манифеста вы можете отслеживать статус обновления:

```bash
kubectl get targetinstallationstate main
```

Пример вывода:

## Получить подробную информацию {#get-details}

Выполните команду:

```bash
kubectl describe targetinstallationstate main
```

В поле `status` отображается:

* `currentVersion` — текущая установленная версия.
* `phase` — фаза обновления:
    * `Pending` — обновление ожидает запуска.
    * `Blocked` — обновление ожидает выполнения обязательных условий. Причина указана в `message`.
    * `Running` — обновление выполняется.
    * `Completed` — обновление выполнено.
    * `Failed` — обновление завершилось с ошибкой.
* `message` — сообщение о текущем состоянии.
* `jobName` — имя задания Kubernetes, выполняющего обновление.
* `lastUpdateTime` — время последнего обновления статуса.

## Просмотреть логи обновления {#view-logs}

Чтобы просмотреть логи задания обновления, выполните команду:

```bash
kubectl logs -n stackland-install job/<имя_задания>
```

Имя задания можно получить из поля `status.jobName` ресурса `TargetInstallationState`.
