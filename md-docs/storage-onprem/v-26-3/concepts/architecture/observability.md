# Observability

Метрики и логи в On-premises Yandex Object Storage делятся на две категории:

* Системные метрики и логи, которые необходимы для отладки при инцидентах. Их объем сравнительно невелик, но необходимо обеспечить их высокую доступность даже при отказе большинства компонентов On-premises Yandex Object Storage.
* Метрики и логи, которые используются в остальных случаях. Их объем многократно больше, но при инцидентах допустимо снижение их доступности.

Для хранения метрик и логов используются Grafana Mimir и Grafana Loki. Для долгосрочного хранения данных они используют S3. Небольшой объем системных метрик и логов хранится в Backup Storage, все остальные — в служебных бакетах самого On-premises Yandex Object Storage.

Схема хранения метрик и логов:

![Хранение метрик и логов](../../_assets/architecture/observability.png)

Все кластеры Mimir и Loki по умолчанию устанавливаются в трех копиях. В этой конфигурации запись и чтение недавних данных доступны при отказе одного хоста, а чтение исторических данных зависит от доступности чтения из соответствующего S3.

Также на схеме отмечены:

- Grafana без сохранения состояния, содержащая набор встроенных дашбордов и доступная при отказе до двух хостов;
- эндпоинт формата Prometheus Federation для сбора метрик из кластера — его доступность совпадает с доступностью соответствующего кластера Mimir;
- Inspector — развернут в Kubernetes и доступен через Console API. При отказе компонентов On-premises Yandex Object Storage может собрать системные метрики и логи напрямую из Backup Storage.
