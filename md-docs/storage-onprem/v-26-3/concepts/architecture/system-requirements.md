## Требования к дискам {#disks}

### Общие требования к дискам {#disks-general}

* Размер одного диска — не менее 1 ТБ.
* Используются одинаковые модели дисков.
* Для HDD не требуется RAID — каждый диск должен быть виден как отдельное блочное устройство в системе.
* Для хранения метаданных необходимы NVMe SSD.
* NVMe SSD объединяются в RAID 1 или RAID 10 программно или аппаратно.
* Boot/system раздел может быть размещен на тех же NVMe SSD.

### Расчет параметров кластера метаданных {#metadata-calculation-methodology}

Расчет помогает определить количество и размер NVMe SSD на каждой машине кластера метаданных исходя из ожидаемой нагрузки. Выберите подходящую конфигурацию из [таблицы типовых конфигураций](#disks-configurations) или рассчитайте значения с помощью калькулятора.

{% note warning %}

Калькулятор рассчитывает минимальный объем метаданных на кластер и на каждый узел без учета избыточности. Полученный объем метаданных — это полезный объем, который должен быть доступен после организации RAID. Например, при использовании RAID 1 суммарный объем дисков на узле должен быть как минимум вдвое больше рассчитанного.

{% endnote %}



Для расчета вручную используйте те же формулы:

1. Рассчитайте объем метаданных на кластер в тебибайтах.

   ```
   Объем метаданных на кластер = (0,004 × <количество_объектов>) + (<средний_RPS> × 0,002)
   ```

   Где:

   * `<количество_объектов>` — количество объектов в миллионах штук.
   * `<средний_RPS>` — среднее количество запросов в секунду.

2. Рассчитайте объем метаданных на узел в тебибайтах. Объем считается без учета избыточности хранения, например зеркалирования дисков в RAID.

   ```
   Объем метаданных на узел = 0,5 + <объем_метаданных_на_кластер> / <количество_узлов_метаданных>
   ```

   Где:

   * `<объем_метаданных_на_кластер>` — объем метаданных на кластер, полученный по предыдущей формуле.
   * `<количество_узлов_метаданных>` — количество узлов в кластере метаданных. Обычно достаточно 4 узлов, но может потребоваться больше при высокой нагрузке по памяти и CPU или повышенных требованиях к отказоустойчивости.

На каждом узле кластера метаданных минимально устанавливаются два NVMe SSD, которые объединяются в RAID 1. Объем диска должен быть не меньше чистого объема метаданных на узел.

Вы можете использовать другие уровни RAID. В этом случае подберите количество дисков так, чтобы чистый объем метаданных на узел был доступен после организации RAID.

### Расчет доступного объема хранилища {#storage-calculation-methodology}

Доступный объем хранилища показывает, сколько места будет доступно для пользовательских данных. Доступный объем хранилища не равен суммарной емкости дисков, так как часть места резервируется для системных нужд, а оставшийся объем уменьшается на коэффициент избыточности.



Калькулятор рассчитывает доступный объем хранилища в тебибайтах по следующей формуле:

```
Доступный объем = (N × S − floor(N × S × P / 100)) × 916 / R / 1024
```

Физический объем хранилища учитывает разметку дисков, но не резерв и избыточность. Он рассчитывается в тебибайтах:

```
Физический объем = N × S × 916 / 1024
```

Где:

* floor — округление в меньшую сторону.
* N — количество дисков хранилища.
* S — размер одного диска в ТБ по спецификации производителя.
* P — резерв хранилища в процентах. Количество резервных блоков округляется вниз.
* 916 — размер блока в ГиБ, используемого в расчете на каждый ТБ диска.
* R — коэффициент избыточности.

{% cut "Пример расчета" %}

Пусть есть 4 машины, на каждой по 12 дисков по 10 ТБ. Резерв 5%, избыточность реализована с помощью репликации, коэффициент 3.

Общее количество дисков:
4 × 12 = 48

Физический объем хранилища:
48 × 10 × 916 / 1024 ≈ 429,4 ТиБ

Доступный объем хранилища:
(48 × 10 − floor(48 × 10 × 5 / 100)) × 916 / 3 / 1024 ≈ 136,0 ТиБ

{% endcut %}

Размер диска задается в ТБ по спецификации производителя. При расчете учитывается разметка дисков блоками по 916 ГиБ. Результаты в ТиБ округляются до одного знака после запятой.

Резерв хранилища нужен для системных операций, дефрагментации и перебалансировки при отказе диска. Если предполагается существенная доля перезаписи (удаление объектов и немедленная запись новых), резерв следует увеличить с учетом процессов дефрагментации HDD. Также чем меньше инсталляция, тем больше следует закладывать резерв.

{% note info %}

Рекомендуемый резерв хранилища — не менее 5%. Резерв можно снизить вплоть до нуля, однако такая конфигурация не рекомендуется — при отказе диска не будет запаса для перебалансировки.

{% endnote %}

Оставшийся после выделения резерва объем используется для хранения с учетом коэффициента избыточности. Избыточность защищает от потери данных и реализуется с помощью [избыточного кодирования и репликации](../data-redundancy.md).

Коэффициент избыточности может быть дробным числом. Например, для схемы с избыточным кодированием (erasure coding) 4+2 используйте коэффициент 1.5.

Для подробного расчета доступного объема хранилища для ваших сценариев обратитесь в [техническую поддержку](../../quickstart.md#support).


## Требования к сети {#network}

### Общие требования к сети {#network-general}

* Отдельные изолированные сегменты сети для IPMI/BMC (1 ГБ/с), Management (1 ГБ/с, web UI, DNS, rsyslog, Prometheus), Internal (2×25 ГБ/с, внутренний трафик репликации/восстановления), Data (2×25 ГБ/с, трафик от/к клиентам S3).
* Скорость интерфейсов зависит от количества дисков в сервере:
    * 4 HDD и меньше — 10 ГБ/с.
    * 4–12 HDD — 25 ГБ/с.
    * 12 HDD и больше — не менее двух линков по 25 ГБ/с.

* На интерфейсах Internal и Data рекомендуется использовать LACP для агрегирования.
* Если LACP недоступен, возможно подключение двух интерфейсов в режиме балансировки нагрузки, но это потребует дополнительных IP-адресов на Data-интерфейсе.
* Настоятельно рекомендуется разместить Data и Internal интерфейсы в разных широковещательных доменах. Настройка в одном домене возможна, но потребует конфигурации статических ARP-записей и может привести к проблемам при масштабировании или миграции.
* Парные линки рекомендуется подключать к разным коммутаторам (mLAG для LACP) или к разным членам стека.


### Требования к портам для настройки файрвола {#network-firewall}

* Data-интерфейсы:
    * входящий TCP 80/443 от клиентов S3 на VIP-адреса S3.

* Internal-интерфейсы:
    * Не рекомендуется фильтровать трафик между машинами Object Storage из-за возможных изменений в будущем.
    * В текущей конфигурации: входящий/исходящий UDP на порт 4789 между машинами Object Storage.

* Management-интерфейс:
    * Входящий TCP 80/443 от администратора на VIP-адреса web UI.
    * Входящий TCP 80/443 от системы мониторинга на VIP-адрес Prometheus.
    * Исходящий TCP/UDP на адрес/порт rsyslog-сервера.

{% note warning %}

Если используется встроенный L2-балансировщик, то Data и Management интерфейсы машин, между которыми будут перемещаться VIP-адреса, должны находиться в одном широковещательном L2-сегменте. Балансировщик использует ARP для анонса VIP-адресов.

{% endnote %}
