# Управление отстающей репликой Yandex StoreDoc

При создании или изменении скрытого хоста вы можете задать время, на которое данные на вторичной реплике отстают от мастера. Такая реплика станет _отстающей_. С нее можно оперативно восстановить данные в случае ошибочного удаления коллекции или базы данных. 

{% note warning %}

В шардированном кластере восстановление данных с отстающей реплики не рекомендуется, так как может привести к несогласованному состоянию кластера. Подробнее в разделе [Отстающие реплики](../concepts/replication.md#delayed-replica).

{% endnote %}

## Настроить отставание реплики в существующем кластере {#set-at-update}

В существующем кластере реплику можно сделать отстающей, если скрыть хост и задать время отставания от мастера. При этом в нешардированном кластере или шарде, к которому относится хост, должно остаться не менее трех нескрытых хостов. Также вы можете задать отставание реплики при [добавлении хоста](hosts.md#add-host).

Если первичную реплику сделать отстающей, будут запущены выборы нового мастера.

О настройке отстающей реплики при создании кластера читайте в разделе [Создание кластера Yandex StoreDoc](cluster-create.md).

{% list tabs group=instructions %}

- Консоль управления {#console}

    1. [Перейдите](https://console.yandex.cloud/link/storedoc) в сервис **Yandex StoreDoc**.
    1. Нажмите на имя нужного кластера и выберите вкладку **Хосты**.
    1. Нажмите значок ![image](../../_assets/console-icons/ellipsis.svg) в строке нужного хоста и выберите пункт **Редактировать**.
    1. Настройте отставание реплики:

        1. Отметьте хост скрытым.
        1. Задайте значение отставания реплики от мастера в секундах.

           Минимальное значение и значение по умолчанию — `0` (нет отставания). Максимальное значение — `31536000` (1 год).

           Отстающая реплика копирует журнал изменений с мастера, но применяет его с лагом, равным времени отставания. Поэтому чем больше время отставания, тем больше потребуется места на диске хоста для хранения изменений до того, как они будут применены.
           
           Подробнее в разделе [Отстающие реплики](../concepts/replication.md#delayed-replica).

    1. Нажмите кнопку **Сохранить**.

- CLI {#cli}

    Если у вас еще нет интерфейса командной строки Yandex Cloud (CLI), [установите и инициализируйте его](../../cli/quickstart.md#install).

    По умолчанию используется каталог, указанный при [создании](../../cli/operations/profile/profile-create.md) профиля CLI. Чтобы изменить каталог по умолчанию, используйте команду `yc config set folder-id <идентификатор_каталога>`. Также для любой команды вы можете указать другой каталог с помощью параметров `--folder-name` или `--folder-id`.
    
    Если вы обращаетесь к ресурсу по имени, поиск будет выполнен в каталоге по умолчанию. Если вы обращаетесь к ресурсу по идентификатору, поиск будет выполнен глобально — во всех каталогах с учетом прав доступа.

    Чтобы настроить отставание реплики, выполните команду:

    
    ```bash
    yc managed-mongodb host update \
      --cluster-name <имя_кластера> \
      --host hostname=<имя_хоста>,`
            `hidden=true,`
            `secondary-delay-secs=<отставание_реплики_в_секундах>
    ```


    Для параметра `secondary-delay-secs` минимальное значение и значение по умолчанию — `0` (нет отставания). Максимальное значение — `31536000` (1 год).

    Отстающая реплика копирует журнал изменений с мастера, но применяет его с лагом, равным времени отставания. Поэтому чем больше время отставания, тем больше потребуется места на диске хоста для хранения изменений до того, как они будут применены.
    
    Подробнее в разделе [Отстающие реплики](../concepts/replication.md#delayed-replica).


- Terraform {#tf}

    Чтобы изменить параметры хоста в кластере:

    1. Откройте актуальный конфигурационный файл Terraform с планом инфраструктуры.

        Инструкция по созданию такого файла приведена в разделе [Создание кластера](cluster-create.md).

        Полный список доступных для изменения полей конфигурации кластера Yandex StoreDoc приведен в [документации провайдера Terraform](../../terraform/resources/mdb_mongodb_cluster.md).

    1. Измените в описании кластера Yandex StoreDoc атрибуты блока `host`, соответствующего отстающей реплике.

        ```hcl
        resource "yandex_mdb_mongodb_cluster" "<имя_кластера>" {
          ...
          host {
            ...
            host_parameters {
              hidden               = <скрытие_хоста>
              secondary_delay_secs = <отставание_реплики_в_секундах>
            }
          }
        }
        ```

        Для параметра `secondary_delay_secs` минимальное значение и значение по умолчанию — `0` (нет отставания). Максимальное значение — `31536000` (1 год).

        Отстающая реплика копирует журнал изменений с мастера, но применяет его с лагом, равным времени отставания. Поэтому чем больше время отставания, тем больше потребуется места на диске хоста для хранения изменений до того, как они будут применены.
        
        Подробнее в разделе [Отстающие реплики](../concepts/replication.md#delayed-replica).

    1. Проверьте корректность настроек.

        1. В командной строке перейдите в каталог, в котором расположены актуальные конфигурационные файлы Terraform с планом инфраструктуры.
        1. Выполните команду:
        
           ```bash
           terraform validate
           ```
        
           Если в файлах конфигурации есть ошибки, Terraform на них укажет.

    1. Подтвердите изменение ресурсов.

        1. Выполните команду для просмотра планируемых изменений:
        
           ```bash
           terraform plan
           ```
        
           Если конфигурации ресурсов описаны верно, в терминале отобразится список изменяемых ресурсов и их параметров. Это проверочный этап: ресурсы не будут изменены.
        
        1. Если вас устраивают планируемые изменения, внесите их:
        
           1. Выполните команду:
        
              ```bash
              terraform apply
              ```
        
           1. Подтвердите изменение ресурсов.
           1. Дождитесь завершения операции.

        {% note warning "Ограничения по времени" %}
        
        Провайдер Terraform ограничивает время на выполнение операций с кластером Yandex StoreDoc:
        
        * создание, в т. ч. путем восстановления из резервной копии, — 30 минут;
        * изменение — 60 минут.
        
        Операции, длящиеся дольше указанного времени, прерываются.
        
        {% cut "Как изменить эти ограничения?" %}
        
        Добавьте к описанию кластера блок `timeouts`, например:
        
        ```hcl
        resource "yandex_mdb_mongodb_cluster" "<имя_кластера>" {
          ...
          timeouts {
            create = "1h30m" # Полтора часа
            update = "2h"    # 2 часа
          }
        }
        ```
        
        {% endcut %}
        
        {% endnote %}


- REST API {#api}

    1. [Получите IAM-токен для аутентификации в API](../api-ref/authentication.md) и поместите токен в переменную среды окружения:

        ```bash
        export IAM_TOKEN="<IAM-токен>"
        ```

    1. Воспользуйтесь методом [Cluster.updateHosts](../api-ref/Cluster/updateHosts.md) и выполните запрос, например с помощью [cURL](https://curl.se/):

        {% note warning %}
        
        Метод API переопределит все параметры изменяемого объекта, которые не были явно переданы в запросе, на значения по умолчанию. Чтобы избежать этого, перечислите настройки, которые вы хотите изменить, в параметре `updateMask` (одной строкой через запятую).
        
        {% endnote %}

        ```bash
        curl \
          --request POST \
          --header "Authorization: Bearer $IAM_TOKEN" \
          --header "Content-Type: application/json" \
          --url 'https://mdb.api.cloud.yandex.net/managed-mongodb/v1/clusters/<идентификатор_кластера>/hosts:batchUpdate' \
          --data '{
                    "updateHostSpecs": [
                      {
                        "updateMask": "hidden,secondaryDelaySecs",
                        "hostName": "<имя_хоста>",
                        "hidden": true,
                        "secondaryDelaySecs": "<отставание_реплики_в_секундах>"
                      }
                    ]
                  }'
        ```

        Для параметра `secondaryDelaySecs` минимальное значение и значение по умолчанию — `0` (нет отставания). Максимальное значение — `31536000` (1 год).

        Отстающая реплика копирует журнал изменений с мастера, но применяет его с лагом, равным времени отставания. Поэтому чем больше время отставания, тем больше потребуется места на диске хоста для хранения изменений до того, как они будут применены.
        
        Подробнее в разделе [Отстающие реплики](../concepts/replication.md#delayed-replica).

        Идентификатор кластера можно запросить со [списком кластеров в каталоге](cluster-list.md#list-clusters).

    1. Убедитесь, что запрос был выполнен успешно, изучив [ответ сервера](../api-ref/Cluster/updateHosts.md#yandex.cloud.operation.Operation).

- gRPC API {#grpc-api}

    1. [Получите IAM-токен для аутентификации в API](../api-ref/authentication.md) и поместите токен в переменную среды окружения:

        ```bash
        export IAM_TOKEN="<IAM-токен>"
        ```

    1. Клонируйте репозиторий [cloudapi](https://github.com/yandex-cloud/cloudapi):
       
       ```bash
       cd ~/ && git clone --depth=1 https://github.com/yandex-cloud/cloudapi
       ```
       
       Далее предполагается, что содержимое репозитория находится в директории `~/cloudapi/`.

    1. Воспользуйтесь вызовом [ClusterService/UpdateHosts](../api-ref/grpc/Cluster/updateHosts.md) и выполните запрос, например с помощью [gRPCurl](https://github.com/fullstorydev/grpcurl):

        {% note warning %}
        
        Метод API переопределит все параметры изменяемого объекта, которые не были явно переданы в запросе, на значения по умолчанию. Чтобы избежать этого, перечислите настройки, которые вы хотите изменить, в параметре `update_mask` (в виде массива строк `paths[]`).
        
        {% cut "Формат перечисления настроек" %}
        
        ```yaml
        "update_mask": {
            "paths": [
                "<настройка_1>",
                "<настройка_2>",
                ...
                "<настройка_N>"
            ]
        }
        ```
        
        {% endcut %}
        
        {% endnote %}

        ```bash
        grpcurl \
          -format json \
          -import-path ~/cloudapi/ \
          -import-path ~/cloudapi/third_party/googleapis/ \
          -proto ~/cloudapi/yandex/cloud/mdb/mongodb/v1/cluster_service.proto \
          -rpc-header "Authorization: Bearer $IAM_TOKEN" \
          -d '{
                "cluster_id": "<идентификатор_кластера>",
                "update_host_specs": [
                  {
                    "update_mask": {
                        "paths": [
                          "hidden",
                          "secondary_delay_secs"
                        ]
                    },
                    "host_name": "<имя_хоста>",
                    "hidden": true,
                    "secondary_delay_secs": "<отставание_реплики_в_секундах>"
                  }
                ]
              }' \
          mdb.api.cloud.yandex.net:443 \
          yandex.cloud.mdb.mongodb.v1.ClusterService.UpdateHosts
        ```

        Для параметра `secondary_delay_secs` минимальное значение и значение по умолчанию — `0` (нет отставания). Максимальное значение — `31536000` (1 год).

        Отстающая реплика копирует журнал изменений с мастера, но применяет его с лагом, равным времени отставания. Поэтому чем больше время отставания, тем больше потребуется места на диске хоста для хранения изменений до того, как они будут применены.
        
        Подробнее в разделе [Отстающие реплики](../concepts/replication.md#delayed-replica).

        Идентификатор кластера можно запросить со [списком кластеров в каталоге](cluster-list.md#list-clusters).

    1. Убедитесь, что запрос был выполнен успешно, изучив [ответ сервера](../api-ref/grpc/Cluster/updateHosts.md#yandex.cloud.operation.Operation).

## Восстановить данные с отстающей реплики {#restore-data}

Чтобы восстановить данные с отстающей реплики, необходимо выполнить дамп базы данных Yandex StoreDoc и восстановить данные из дампа на мастере. Эти действия могут выполняться:

* С вашего компьютера через интернет, если вы настроили публичный доступ для отстающей реплики. При этом используется только SSL-соединение.

  Перед подключением [получите SSL-сертификат](connect/index.md#get-ssl-cert).

* С виртуальных машин Yandex Cloud, расположенных в той же [облачной сети](../../vpc/concepts/network.md). Если к отстающей реплике нет публичного доступа, использовать SSL-соединение необязательно.

{% note warning %}

На создание дампа БД может потребоваться время, превышающее отставание реплики. В этом случае ошибочная операция будет применена на отстающей реплике и вы не сможете восстановить данные. Чтобы избежать этого, заранее оцените время на создание дампа и при необходимости увеличьте время отставания реплики.

{% endnote %}

Чтобы восстановить данные с отстающей реплики в нешардированном кластере:

1. Установите `mongodump` и дополнительные утилиты для работы с Yandex StoreDoc. Пример для [Ubuntu 20.04 LTS](https://yandex.cloud/ru/marketplace/products/yc/ubuntu-20-04-lts):

    ```bash
    wget -qO - https://www.mongodb.org/static/pgp/server-4.4.asc | sudo apt-key add -
    echo "deb [ arch=amd64 ] https://repo.mongodb.org/apt/ubuntu focal/mongodb-org/4.4 multiverse" | sudo tee /etc/apt/sources.list.d/mongodb-org-4.4.list
    sudo apt update
    sudo apt install mongodb-org-shell mongodb-org-tools
    ```

1. [Получите FQDN хоста](connect/index.md#get-fqdn) для отстающей реплики и мастера.
1. Создайте дамп базы данных:

   {% list tabs group=instructions %}

   - Подключение с SSL {#with-ssl}

       ```bash
       mongodump --host <FQDN_отстающей_реплики> \
                 --port 27018 \
                 --username <имя_пользователя> \
                 --password "<пароль>" \
                 --ssl \
                 --sslCAFile ~/.mongodb/root.crt \
                 --db <имя_БД> \
                 --out ~/db_dump
       ```

   - Подключение без SSL {#without-ssl}

       ```bash
       mongodump --host <FQDN_отстающей_реплики> \
                 --port 27018 \
                 --username <имя_пользователя> \
                 --password "<пароль>" \
                 --db <имя_БД> \
                 --out ~/db_dump
       ```

   {% endlist %}

1. Восстановите ошибочно удаленную или измененную коллекцию базы данных из дампа с помощью утилиты `mongorestore`. Предварительно [добавьте](cluster-users.md#updateuser) пользователю [роль mdbDbAdmin](../concepts/users-and-roles.md#mdbDbAdmin).

   {% list tabs group=instructions %}

   - Подключение с SSL {#with-ssl}

       ```bash
       mongorestore --host <FQDN_мастера> \
                    --port 27018 \
                    --username <имя_пользователя> \
                    --password "<пароль>" \
                    --ssl \
                    --sslCAFile ~/.mongodb/root.crt \
                    --nsInclude '<имя_БД>.<имя_коллекции>' \
                    --authenticationDatabase=<имя_БД> ~/db_dump
       ```

   - Подключение без SSL {#without-ssl}

       ```bash
       mongorestore --host <FQDN_мастера> \
                    --port 27018 \
                    --username <имя_пользователя> \
                    --password "<пароль>" \
                    --nsInclude '<имя_БД>.<имя_коллекции>' \
                    --authenticationDatabase=<имя_БД> ~/db_dump
       ```

   {% endlist %}

   Чтобы восстановить всю базу данных из дампа, выполните следующую команду:

   {% list tabs group=instructions %}

   - Подключение с SSL {#with-ssl}

       ```bash
       mongorestore --host <FQDN_мастера> \
                    --port 27018 \
                    --username <имя_пользователя> \
                    --password "<пароль>" \
                    --ssl \
                    --sslCAFile ~/.mongodb/root.crt
                    --nsInclude '*.*' \
                    --authenticationDatabase=<имя_БД> \
                    --drop ~/db_dump
       ```

   - Подключение без SSL {#without-ssl}

       ```bash
       mongorestore --host <FQDN_мастера> \
                    --port 27018 \
                    --username <имя_пользователя> \
                    --password "<пароль>" \
                    --nsInclude '*.*' \
                    --authenticationDatabase=<имя_БД> \
                    --drop ~/db_dump
       ```

   {% endlist %}

   {% note warning %}

   При восстановлении всей БД записи во всех коллекциях будут восстановлены в состояние на момент отставания.

   {% endnote %}
