# Подключение к Yandex Cloud Registry из сети Yandex Virtual Private Cloud без доступа в интернет


В этом руководстве вы развернете в Yandex Cloud облачную инфраструктуру для организации доступа к [реестру](../../../cloud-registry/concepts/registry.md) Cloud Registry с ресурсов, которые размещены в облачной сети Virtual Private Cloud (VPC) и не имеют доступа в интернет.

Приватная сетевая связность ресурсов в облачной сети с сервисом Cloud Registry будет организована с использованием [сервисных подключений](../../../vpc/concepts/private-endpoint.md) (_private endpoints_) VPC.

## Схема решения {#flowchart}

![pencil](../../../_assets/tutorials/cloud-registry-via-pe/flowchart.svg)

На схеме:

* Сервис [Yandex Cloud DNS](../../../dns/index.md) разрешает имя `registry.yandexcloud.net` во [внутренний IP-адрес](../../../vpc/concepts/address.md#internal-addresses) сервисного подключения Cloud Registry.
* Через это сервисное подключение [Docker](https://www.docker.com/) обращается к Cloud Registry по HTTPS.
* Для операций с данными артефактов также используется сервисное подключение [Yandex Object Storage](../../../storage/index.md). [Ресурсные записи](../../../dns/concepts/resource-record.md), созданные для имен `storage.yandexcloud.net` и `*.storage.yandexcloud.net`, указывают на внутренний IP-адрес сервисного подключения Object Storage.
* Для обращения к реестру Cloud Registry с тестовой [виртуальной машины](../../../compute/concepts/vm.md) доступ в интернет не требуется.


## Ресурсы в создаваемой инфраструктуре {#resources}

В приведенных инструкциях и примерах команд для развертывания необходимой инфраструктуры создаются следующие ресурсы:

* [Облачная сеть](../../../vpc/concepts/network.md#network) `cr-private-net`.
* [Подсеть](../../../vpc/concepts/network.md#subnet) `cr-private-subnet` в [зоне доступности](../../../overview/concepts/geo-scope.md) `ru-central1-a`. [CIDR](https://ru.wikipedia.org/wiki/Бесклассовая_адресация) подсети `192.168.10.0/24`.
* [Сервисное подключение Object Storage](../../../storage/concepts/bucket.md#access-via-vpc) `storage-pe` со статическим внутренним IP-адресом `192.168.10.10`.
* Сервисное подключение Cloud Registry `cloud-registry-pe` со статическим внутренним IP-адресом `192.168.10.11`.
* Тестовая виртуальная машина `cr-private-vm` без доступа в интернет. ВМ будет создана в зоне доступности `ru-central1-a` в подсети `cr-private-subnet` со статическим внутренним IP-адресом `192.168.10.20`.
* [Сервисный аккаунт](../../../iam/concepts/users/service-accounts.md) `cr-pusher`, который будет привязан к виртуальной машине и от имени которого будет осуществляться доступ к [артефактам](../../../cloud-registry/concepts/artifacts/index.md) в реестре.
* [Реестр](../../../cloud-registry/concepts/registry.md) Cloud Registry `cr-private-demo`.
* Тестовый [Docker-образ](../../../cloud-registry/concepts/artifacts/docker.md) `hello-world:pe-demo`, который будет загружен в реестр и затем скачан из него на тестовой ВМ.
* Служебная виртуальная машина `jump-vm` с доступом в интернет, которая будет использоваться для подключения по SSH к тестовой виртуальной машине.

При необходимости замените адреса, имена и идентификаторы ресурсов на подходящие для вашего [каталога](../../../resource-manager/concepts/resources-hierarchy.md#folder). Убедитесь, что выбранные IP-адреса относятся к выбранной подсети и не заняты другими ресурсами.

## Ограничения и предварительные условия {#limitations}

{% note alert %}

Сервисные подключения обеспечивают приватную сетевую связность между виртуальной машиной и реестром, но не отключают [публичный эндпоинт](../../../api-design-guide/concepts/endpoints.md) сервиса Cloud Registry. Создаваемая основная DNS-запись изменяет разрешение публичного [FQDN](../../../glossary/fqdn.md) внутри выбранной облачной сети, при этом из других сетей реестр Cloud Registry остается доступен через публичный эндпоинт.

Контроль доступа к артефактам в реестрах Cloud Registry должен осуществляться средствами [Yandex Identity and Access Management](../../../iam/concepts/access-control/index.md).

{% endnote %}

Чтобы создать инфраструктуру для реализации решения, пользователь Yandex Cloud должен обладать [правами доступа](../../../iam/concepts/access-control/roles.md), достаточными для создания всех [ресурсов](#resources), которые описаны выше.

Перед прохождением руководства [убедитесь](https://console.yandex.cloud/cloud?section=quotas), что в вашем облаке достаточно свободных квот для создания ресурсов.

При прохождении руководства также учитывайте следующее:

* Необходимая инфраструктура включает в себя два сервисных подключения. По умолчанию [квота](../../../vpc/concepts/limits.md#vpc-quotas) на количество сервисных подключений (`vpc.privateEndpoints.count`) составляет два подключения на одно облако. Таким образом, инфраструктура для этого руководства может занять эту квоту целиком.
* В одной облачной сети можно создать не более одного сервисного подключения каждого типа. Если вы планируете использовать имеющуюся сеть и в ней уже есть сервисное подключение Object Storage или Cloud Registry, используйте имеющееся сервисное подключение.
* Сервисное подключение является региональным и распределено по зонам доступности.

## Способы создания инфраструктуры {#deployment-options}

Инфраструктуру для реализации решения вы можете создать с помощью одного из инструментов:

* [Консоль управления, CLI, API](console.md) — используйте консоль управления Yandex Cloud, CLI или API, чтобы создать инфраструктуру в пошаговом режиме.
* [Terraform](terraform.md) — используйте этот способ, чтобы упростить создание ресурсов и управление ими, используя подход «инфраструктура как код» (IaC). Скачайте пример конфигурации Terraform из репозитория на GitHub, а затем разверните инфраструктуру с помощью [Terraform-провайдера Yandex Cloud](../../../terraform/index.md).
